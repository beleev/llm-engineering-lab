# M39 — KV 淘汰: 按重要性永久丢弃 KV, 后面问到的就答不出来

[llm_infer 目录](../README.md) · [交互实验](https://beleev.github.io/llm-engineering-lab/#/infer/attention-sinks)

## 直觉

长上下文的 KV cache 放不下时, 最直接的办法是只留预算内的 B 个 token, 其余删掉。m16 的 sink + 窗口已经是一种淘汰, 它只看位置: 留开头几个和最近一段。H2O、SnapKV、TOVA、PyramidKV 改成按"重要性"留, 重要性来自注意力分数, 同样预算下能留住前文中段被问到的那句话。
代价在于淘汰是不可逆的。打分只能根据到现在为止出现过的 query 判断谁重要, 当时没人问的信息被删掉后, 后面再问就答不出来。
和另外两条路对照:
- **m22 的 Quest**: KV 全部留着, 每步只读打分最高的几个 block。省的是读取带宽, 显存一点没省, 但任何时候问什么都还找得回来。
- **m20 的分层 offload**: 把放不下的 KV 挪到 CPU 内存或磁盘, 需要时搬回来, 也不丢信息。

## 核心原理

### 核心数据结构或公式

所有策略都返回"留下哪些位置", 没留下的位置之后任何 query 都看不到。

| 策略 (kv_eviction.py) | 按什么留 | 什么时候删 |
|---|---|---|
| sink + 窗口 (`sink_window_keep`, m16 同一规则) | 位置: 开头 4 个 + 最近 B−4 个 | 每写入一个 token |
| TOVA (`tova_keep`) | 当前 query 的注意力, 删最低的那个 | 写满之后每写入一个 token |
| H2O (`H2O`) | 累积注意力 (每个 token 被所有 query 看过多少) 选 B/2 个重击者, 再留最近 B/2 个 | prefill 结束时选一次, 之后每步删 1 个 |
| SnapKV (`snapkv_keep`) | prompt 末尾 16 个 query (观察窗口, 通常就是用户的问题) 对前文的注意力求和投票, 1D max pool (kernel 7) 后取 top | prefill 结束时压一次, 生成阶段写入的不压 |
| Quest (m22 的 `quest_upper_bound` + `select_blocks`) | 当前 query 对每个 block 的 min/max 上界 | 不删, 每步重选 |

```
H2O 打分     score_j = Σ_t softmax(q_t · K / √d)_j          对 prompt 内所有 t ≥ j 求和
SnapKV 投票  vote_j  = Σ_{t ∈ 观察窗口} softmax(q_t · K / √d)_j,  pooled = maxpool(vote, 7)
合成对话     位置 0 = sink (key 沿所有 query 共有的方向 u); 针 A、B 各 2 个 token, key 沿方向 a / b, value = 答案向量
             问题 1 和回答 1 的 query 加 4.5·a, 问题 2 的 query 加 4.5·b, 对针的打分 ≈ 18
答对         输出里正确答案向量的比例超过一半
```

PyramidKV 在 SnapKV 的基础上按层分配预算, 低层多、高层少 (等差递减), 依据是注意力在高层更集中。单层设定下体现不出来, 这里没有实现。

断言:
- 20 个种子上, 完整 cache 和 Quest 两个问题都全对。
- 淘汰策略答对与否完全取决于针是否还在 cache 里 (逐个种子逐个问题检查)。
- H2O 和 SnapKV 的打分里有问题 1 的 query, 针 A 每次都留下; 问题 2 答对不超过 30%。
- sink + 窗口一个都答不对; TOVA 在问题 1 到来前已把针 A 删掉, 问题 1 答对不超过 30%。
- 两个问题对调后, H2O 和 SnapKV 先问的那个全对, 后问的不超过 30%。
- Quest 存全部 2080 个 token 的 KV, 每步只读 256 个; 其余淘汰策略的 cache 始终不超过预算。

**怎么读**: SnapKV 在 20 个种子里有 3 次答对了问题 2, 因为它留下了 prompt 的 12.5%, 针 B 偶尔落在被留下的邻居里 (seed 0 就是一次)。这是运气, 不是能力。
[3] 把两个问题对调后, 同一个 SnapKV 先问 B 时 20/20 全对: 打分本身没问题, 失败只来自"删掉的东西回不来"。

## 与真实系统的差距

- 单层单头的合成注意力, 不是真实模型。真实模型有几十层、每层多个头, H2O / SnapKV 按头分别选, PyramidKV 按层分预算, 效果要在 LongBench、Needle-in-a-Haystack 这类评测上量。
- 论文数字 (摘要): H2O 用 20% 的重击者, 在 OPT-6.7B/30B 上吞吐比 DeepSpeed Zero-Inference / HF Accelerate / FlexGen 高 29× / 29× / 3×; SnapKV 在 16K 输入时生成快 3.6 倍、显存效率高 8.2 倍; TOVA 有时用 1/8 的 cache 接近完整模型; PyramidKV 在 LongBench 上留 12% 的 KV 与完整 KV 持平。这些都是在"问题在 prompt 末尾"的评测设定下测的, 多轮对话里后问的问题不在其中。
- H2O 原文在生成时逐步淘汰; 这里 prefill 结束时按 prompt 内的累积注意力一次选满, 之后每步删 1 个。
- 真实实现按 page 或 block 删, 还要处理 RoPE 位置; 这里按单个 token 删, key 不带位置编码。
- 合成数据的参数 (sink 的强度、针的打分 ≈ 18、普通 key 的幅度) 是设定的; 针越弱, 各策略的差别越模糊。

## 常见误区

- "SnapKV 压完还能答任何问题" —— 它按 prompt 末尾的问题投票。后面换一个问题, 被删的前文回不来 (问题 2 只在 3/20 的种子上碰巧答对)。
- "H2O 的重击者就是重要的 token" —— 是被已经出现过的 query 看得多的 token。累积分数还偏向靠前的位置, 因为它们被更多 query 看过。
- "Quest 和 SnapKV 都是稀疏注意力, 一回事" —— Quest 不删, 显存不省, 每个 query 现选; SnapKV 删, 显存省了, 但只对压缩时的问题有效。
- "sink + 窗口和 H2O 只是打分不同" —— sink + 窗口完全不看内容, 前文中段的任何信息都留不住 (20 个种子全错)。

## 自测题

1. 预算 256, prompt 2048, SnapKV 为什么有时也能答对没被问过的问题 2?
   **答**: 它保留了 prompt 的 12.5%, 针 B 偶尔恰好落在被留下的位置或被 max pool 带上的邻居里。答对与否完全取决于针是否碰巧还在, 20 个种子里是 3 次。
2. TOVA 为什么连问题 1 都答不对, 而 H2O 和 SnapKV 能?
   **答**: TOVA 在写入前文时就按当前 query 的注意力逐个删除, 问题 1 还没到, 针 A 和普通 token 没有区别, 早早被删了。H2O 和 SnapKV 在 prompt 全部到齐后才打分, 打分里有问题 1 的 query。
3. 想支持多轮对话里"前文任何内容都可能被问到", 该选淘汰还是 Quest / offload?
   **答**: Quest 或 offload。淘汰省显存但不可逆; Quest 留着全部 KV 只少读, offload 把 KV 挪到更便宜的存储, 都能在后面的问题到来时找回信息, 代价是显存或搬运带宽。
