# m35 — 混合模型的状态缓存: KV 能截断, 递推状态只能存快照

[llm_infer 目录](../README.md) · [交互实验](https://beleev.github.io/llm-engineering-lab/#/infer/hybrid-state)

## 直觉

Qwen3-Next 这类混合模型每 4 层里有 3 层是 Gated DeltaNet (线性注意力), 只有 1 层是全注意力。全注意力层照常给每个 token 存一行 K/V, 递推层则把整段前缀压进一个定长的状态矩阵 $S$。推理引擎里很多优化都建立在「KV 可以按 token 截断」上: 前缀缓存把前 $L$ 个 token 的 KV 直接拿来用, 投机解码在草稿被拒时把多算的那几行 KV 截掉。状态矩阵没有这个操作, 从位置 100 的状态里切不出位置 77 的状态。

所以服务混合模型时, 注意力层的 KV 照常分页, 递推层要另想办法:
- 前缀缓存: 在检查点位置存状态快照, 命中长度只能落在快照位置上。快照越密, 命中越长, 显存也越多。
- 投机解码回滚: KV 截断即可; 状态要么在验证时逐位置留快照, 要么从验证前的快照把接受的 token 重算一遍。
- MTP 自投机: DeepSeek-V3 和 Qwen3-Next 训练时带了 MTP (multi-token prediction) 头, 推理时可以直接拿它当草稿, 不需要独立的草稿模型。接受率取决于这个头训练得好不好。

## 核心原理

### 核心数据结构或公式

```
Gated DeltaNet 一层 (单头)   S_t = α_t (I − β_t k_t k_tᵀ) S_{t−1} + β_t k_t v_tᵀ,   o_t = S_tᵀ q_t
                              S ∈ R^{d_k×d_v}, 不随序列长度变; α_t 是遗忘门, β_t 是写入强度
HybridCache                   states: 每个递推层一个 (d_k, d_v)        kv: 每个注意力层 (K, V), 行数 = token 数
truncate_kv(n)                KV 截到前 n 行就等于「只看过前 n 个 token」; states 没有对应操作

PrefixStateCache(interval)    存序列时每喂完 interval 个 token 存一份 states 快照
match                          公共前缀 L → 可用命中 h = ⌊min(L, len−1) / interval⌋ · interval
                              KV 取前 h 行, states 取位置 h 的快照, 剩下的 token 现算

字节账                        KV/token = n_attn · 2 · kv_heads · head_dim · bytes
                              一份快照 = n_rec · (heads · d_k · d_v + 卷积缓存) · bytes
                              快照比同一段的 KV 还大 ⇔ 快照间隔 < 一份快照 ÷ (KV/token)

speculative_generate          验证 k+1 个位置后接受 n 个草稿:
  per_step                    验证时每喂一个 token 存一份 states, 取第 n 份            多占 k+1 份状态
  recompute                   只存验证前那份, 恢复后把接受的 n+1 个 token 重喂一遍      多花 n+1 个 token 的前向
  truncate_only               只截 KV, states 留在「看过全部草稿」的样子                错的, 作对照

MTPHead                       ĥ_{t+1} = [h_t ; emb(x_{t+1})] W,  草稿 = argmax(主模型输出头(ĥ_{t+1}))
                              链式用 k 次; W 随机 = 没训练, fit = 用主模型自己的隐状态做最小二乘
```

读代码时盯住两处:
1. HybridLM.step 里 `S = a * (S - b * np.outer(k, k @ S)) + b * np.outer(k, v)` 这一行: 整段前缀都压在这个矩阵里, 后面所有麻烦都来自它不能按位置切开。
2. speculative_generate 里三种 rollback 的分支: KV 都是一句 truncate_kv, 状态各有各的代价。

断言:
- [1] 带缓存的增量生成与每步整段重算的 logits 最大差 < 1e-4; 状态字节不随长度变, KV 字节随长度涨。
- [2] 每个间隔下命中长度都等于 77 向下取整到间隔的倍数, 从快照续算与整段重算一致; 间隔越大, 命中不变长、快照字节变少; 拿更长序列的最终状态冒充第 77 位的状态, 最大误差 > 0.1。
- [3] 快照比 32K 上下文的 KV 还大, 当且仅当快照间隔小于 1608 token; 3:1 混合后每 token KV 是全注意力的 1/4。
- [4] 逐位置快照和从快照重算的输出都与贪心逐 token 相同, 只截断 KV 的不同; 逐位置快照多存 K+1 = 4 份状态; 从快照重算确实发生了重算。
- [5] 两种主模型上拟合过的 MTP 头接受率都高于没训练的; 随机权重主模型上拟合的头 < 20%, 植入后继表后 > 50%; 接受率再低, 输出也与贪心相同。

几个数字的来历:
- [3] 的数字是按 Qwen3-Next-80B-A3B 的 config.json 算的估算: 48 层, 每 4 层 1 层全注意力 (2 个 KV 头 × 256 维); 36 个 Gated DeltaNet 层各有 32 个 value 头, 每头一个 128×128 的状态, 另加 kernel=4 的短卷积缓存最近 3 步的 8192 维。状态按 bf16 算, 引擎如果用 fp32 存状态, 快照大小翻倍。
- [4] 的「只截断 KV」接受率和另外两行不同, 是因为它的状态错了, 生成的序列从中途就已经不是贪心序列。
- [5] 随机权重主模型的贪心输出几乎没有规律, 线性 MTP 头拟合后接受率也只有 9.6%。植入后继表 (logits 加 3·onehot(succ[x])) 之后, 主模型的输出有一部分由当前 token 决定, 没训练的头靠共用的输出头就能猜中 41.3%, 拟合后到 52.3%。这一行用的是植入了结构的合成模型, 不是真实模型的接受率。

## 与真实系统的差距

- 递推层只有单头, 没有短卷积和 MLP。真实 Gated DeltaNet 在 q/k/v 前有一层 kernel=4 的因果卷积, 它的缓存也是状态, 回滚和快照时要和 $S$ 一起处理。
- vLLM 的混合模型前缀缓存只在 block 边界存 Mamba 类状态, 官方文档写明命中只能从 block 边界继续。为了让一页状态和一页注意力 KV 一样大, 引擎会把注意力层的 block_size 调大, 于是快照间隔就是这个 block_size, 比纯注意力模型常用的 16 大得多。文档另给了 --enable-mamba-shared-prefix-checkpoint 配合 --prefix-match-unit, 用来在更细的粒度上命中共享前缀。
- SGLang 的官方文档把状态快照叫 checkpoint: 前缀缓存只能复用到存过 checkpoint 的位置。默认在分叉点和请求结束处存, --hybrid-cache-checkpoints-level 3 时另外每个 prefill chunk 存一次, decode 阶段每 --mamba-track-interval 个 token (默认 256) 存一次。
- Marconi (MLSys 2025) 的准入策略只在 radix 树的分叉点和最后一次 decode 之后存状态, 淘汰时按「省下的 FLOPs ÷ 状态字节」加上最近访问时间打分。这里的 PrefixStateCache 只有固定间隔一种策略, 不淘汰。
- 前缀缓存和 MTP 投机解码叠加时最容易出正确性问题。vLLM issue #43559 报告 Qwen3.6 35B-A3B 同时开 prefix caching 和 MTP 后准确率掉约 20%; PR #47861 分析的原因是把 KV 的「多看一步再丢掉」套到了 Mamba/GDN 状态上, 而递推状态不能像 KV 那样回退 (这个 PR 没有合并, 修复拆进了别的 PR)。[4] 的「只截断 KV」就是这一类错误的最小复现。
- 验证时逐 token 喂给模型, 结果与一次并行前向相同, 但没有并行的速度。真实引擎在一次前向里算完 k+1 个位置, 逐位置快照要在 kernel 里顺手把中间状态写出来。
- MTP 头是一个线性映射, 用主模型自己生成的 2520 个样本做最小二乘。DeepSeek-V3 的 MTP 模块带一个 Transformer 块, 和主模型一起训练, 论文报告第二个 token 的接受率在 85%–90%, 生成速度 (TPS) 是 1.8 倍。

## 常见误区

- 「线性注意力层没有 KV cache, 所以混合模型的缓存问题更简单」: 状态虽然小, 但它是整段前缀的函数, 不能截断。前缀缓存和投机解码都要为它另加快照, 快照一密, 字节数就超过 KV ([3]: 间隔 512 时 2,412 MiB, KV 只有 768 MiB)。
- 「前缀命中多少 token 就省多少 token」: 混合模型的命中要向下取整到快照位置 ([2]: 公共前缀 77, 间隔 16 时只能用 64)。
- 「草稿被拒后把 KV 截掉就回滚完了」: 递推层的状态已经吃进了被拒的 token, 不恢复就会算错 ([4]: 3 条里 0 条与贪心相同)。
- 「MTP 头接受率是模型结构决定的」: 同一个结构, 没训练的头和拟合过的头差很多 ([5]); 主模型输出本身越可预测, 草稿越容易猜中。

## 自测题

1. 混合模型的快照间隔取 512 token, 一个请求和缓存里的序列共享了 1500 个 token, 能命中多少? 剩下要现算多少?
   **答**: ⌊1500 / 512⌋ · 512 = 1024 个; 剩下的 476 个公共 token 加上请求自己新的部分都要现算。
2. 按 [3] 的估算, Qwen3-Next 一份状态快照相当于多少 token 的 KV? 快照间隔取 512 时, 快照和 KV 哪个占显存多?
   **答**: 约 1608 个 token。间隔 512 小于 1608, 每 512 个 token 就多存一份相当于 1608 个 token KV 的快照, 快照占得更多 (32K 上下文时 2,412 MiB 对 768 MiB)。
3. 投机解码每轮验证 k=3 个草稿, 「逐位置快照」和「从快照重算」分别多付出什么? 什么情况下后者几乎不花额外代价?
   **答**: 前者每轮多存 k+1 = 4 份状态 (显存); 后者只存 1 份, 但每次有草稿被拒都要把接受的 n+1 个 token 重新前向一遍 (算力)。草稿全部被接受时不需要重算, 所以接受率越高, 从快照重算越便宜。
