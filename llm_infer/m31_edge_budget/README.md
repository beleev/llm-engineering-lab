# 端侧预算: 能放下、能跑快、能持续吗

## 直觉

这组实验不跑模型, 而是用一组公开假设给端侧设备 (手机这类在本地跑模型的设备) 算三笔账:
- 装不装得下 2 GiB 内存。
- 每生成一个 token 要多少毫秒。
- 要多少焦耳能量。
1B 参数模型的内存账:
- 按 FP16 (每个参数 16 位, 2 字节) 算权重 1907.35 MiB, 加 192 MiB KV (KV cache, 生成时为每个历史 token 缓存的 K、V 向量) 和 256 MiB 运行时共 2355.35 MiB, 2 GiB 装不下。
- 改 INT4 (每个参数 4 位) 后权重 476.84 MiB, 总 924.84 MiB 装得下。
设备持续发热后会降频, demo 把这种热降频模拟成内存带宽减半, 每 token 从 28.053 ms 变成 56.106 ms。手机上能加载模型只是第一关: 上下文缓存、功率和持续运行后的降频都可能成为瓶颈。

## 核心原理

总内存包括权重、KV cache、工作区和运行时:
- 权重是模型参数本身。
- KV cache 随上下文变长而变大。
- 工作区放计算时的中间结果 (demo 没有单独计算)。
- 运行时是推理程序自身占的内存, demo 按 256 MiB 计。
demo 的 KV 按 24 层、8 个 KV 头、每头 64 维、4096 个 token 的上下文、每个数 2 字节计算, K 和 V 各一份, 合计 192 MiB。
KV 有两点容易被忽略:
- 量化权重不自动量化 KV: 本例 INT4 后权重只剩 476.84 MiB, 4096 上下文的 16 位 KV 仍是 192 MiB, 因为量化只改了存参数用的位数, KV 是推理时现算出来的另一份数据, 仍按 16 位存。
- 长上下文下, 缓存会吞掉原本省下的内存: KV 和上下文长度成正比, 上下文翻倍, 这 192 MiB 也翻倍。

简化 roofline 取 max(运算量/算力, 搬运量/带宽), 按它算 decode 卡在带宽上。1 TFLOP/s 下 1B 参数算一个 token 只要 2 ms, 25 GB/s 搬 FP16 权重加 KV 要 88.053 ms。
roofline 模型说的是, 一步计算的耗时由两件事里更慢的那件决定:
- 做完全部运算要多久。
- 把需要的数据从内存搬到计算单元要多久。
decode 是逐个生成 token 的阶段, 每生成一个 token, 每个参数大约参与一次乘法和一次加法, 共 20 亿次运算, 1 TFLOP/s (每秒一万亿次浮点运算) 下只要 2 ms; 但它要把全部权重和 KV 从内存读一遍, FP16 下约 2.2 GB, 25 GB/s 的带宽要 88.053 ms, 所以瓶颈是带宽而不是算力。
再用功率×时间估每 token 能量 (6 W 下 0.52832 J); 热降频把持续带宽砍半, 冷启动峰值不能代表十分钟后的速度: INT4 下刚启动时每 token 28.053 ms, 带宽减半后变成 56.106 ms。

联合设计从目标质量和设备约束出发, 选模型宽深、量化格式、编译器布局与内核; 理论压缩要有算子支持才兑现。联合设计是指模型和软硬件一起挑, 而不是先训好模型再硬塞进设备:
1. 先定要达到的质量和设备的内存、带宽、功率。
2. 再决定模型多宽多深、权重用几位、编译器怎么排布数据、用哪些内核 (执行运算的底层函数)。
如果设备上没有直接计算 INT4 的内核, 就得先把权重解码回高位宽再算, 本例的预算模型没有计入这笔量化解码开销。电池寿命还取决于整机其他负载和电源效率: demo 的 6 W 是整机系统功耗的假设, 屏幕、网络等其他负载和电源转换的损耗都会改变真实续航。

Green AI 要报告每成功任务能耗、硬件利用率、重试和生命周期假设。Green AI 关心 AI 系统用掉多少能源, 只报每 token 能耗不够:
- 任务失败要重试, 重试的能耗要算到最终成功的那一次上。
- 硬件利用率低说明有算力在空转。
- 生命周期假设要说明设备制造、使用年限这些摊进来的部分怎么算。
低功率设备跑得更久, 总能量不一定更低: 能量等于功率乘时间, 降频后如果时间涨得比功率降得多, 每 token 的能量反而上升。本例热降频下每 token 从 0.16832 J 升到 0.33664 J, 因为 demo 只把带宽减半, 功耗仍按 6 W 算, 时间翻倍能量也翻倍; 真实设备降频时功耗也会变, 要实测。没有设备实测就不能给碳排或续航承诺。

## 怎样验证

全部参数都是公开假设 (1B 参数、2 GiB 内存、25 GB/s 带宽、1 TFLOP/s 算力、6 W 功耗), 切换 FP16 / INT4 / 热降频三种情形, 比较总内存能否装入 2 GiB、每 token 毫秒和焦耳。
三种情形每次只改一个量:
- FP16 和 INT4 只差权重位数。
- 热降频在 INT4 的基础上只把带宽减半。
判定看总内存是否不超过 2 GiB, 以及毫秒和焦耳谁高谁低。真实选型还要实测量化质量、温度、功率曲线和电池。

## 与真实系统的差距

预算模型，不是手机或芯片跑分，不提供特定设备续航承诺。真实能耗需扣除/报告空闲基线并说明测量边界。

## 常见误区与自测

权重从 FP16 改 INT4, 峰值内存一定降为四分之一吗?

<details><summary>展开解析</summary>

不一定。只有权重按位宽缩小 (从 1907.35 降到 476.84 MiB), KV 192 MiB、运行时 256 MiB 原样留着; 总内存从 2355.35 降到 924.84 MiB, 远不到四分之一。
三项分开看:
- FP16 每个参数 16 位, INT4 每个参数 4 位, 所以只有权重这一项变成原来的四分之一。
- KV cache 是推理时为上下文存的 K、V 向量, 仍按 16 位存, 和权重位宽无关。
- 运行时的 256 MiB 也不随权重变。
如果真降到四分之一, 总内存应该约 589 MiB, 实际是 924.84 MiB, 约为原来的 39%。上下文越长, KV 占的比例越大, 离四分之一越远。

</details>
