# 端侧预算: 能放下、能跑快、能持续吗

## 直觉

本实验不实际运行神经网络权重, 而是基于公开硬件与模型参数假设, 为本地端侧设备建立三项部署预算账本:
- 总内存占用能否装入 2 GiB 物理上限。
- 自回归阶段每生成单个 token 消耗多少毫秒延迟。
- 每生成单个 token 消耗多少焦耳电能。
针对 1B 参数模型的内存核算对比如下:
- FP16 方案 (每参数 16 位即 2 字节) 权重占用 1907.35 MiB, 加上 192 MiB 的 KV cache 与 256 MiB 运行时开销后总计 2355.35 MiB, 超出 2 GiB 容量限制。
- INT4 方案 (每参数 4 位) 将权重压缩至 476.84 MiB, 总内存降至 924.84 MiB, 满足装载要求。
端侧设备持续高负载运行会触发热降频, 实验将其建模为有效内存带宽减半, 单 token 延迟随之从冷启动的 28.053 ms 翻倍至 56.106 ms。模型能够装入端侧内存只是部署起点, 长上下文 KV cache 膨胀、整机功耗上限与持续运行后的热降频均可能成为实际瓶颈。

## 核心原理

端侧推理峰值内存由模型权重、KV cache、临时工作区与运行时开销四部分共同构成:
- 模型权重存储静态网络参数。
- KV cache 随上下文序列长度线性增长。
- 临时工作区存放算子中间激活张量 (本预算模型未单独单列)。
- 运行时开销代表推理引擎自身占用的固定内存, 本例按 256 MiB 计入。
本例的 KV cache 按 24 层、8 个 KV 头、每头维度 64、上下文长度 4096 个 token、每元素 2 字节计算, K 与 V 各存一份, 合计 192 MiB。
工程核算中 KV cache 有两项关键边界极易被忽视:
- 仅量化模型权重并不会自动压缩 KV cache: 本例权重经 INT4 量化后降至 476.84 MiB, 但 4096 长度的 16 位 KV cache 仍占 192 MiB, 因为 KV 向量由推理过程动态算出并默认按 16 位浮点缓存。
- 长上下文会迅速侵蚀权重量化省出的内存空间: KV cache 容量与序列长度成正比, 上下文翻倍则这 192 MiB 缓存开销同步翻倍。

简化 roofline 模型取计算耗时与访存耗时的较大值 $\max(\text{运算量}/\text{算力}, \text{搬运量}/\text{带宽})$, 据此核算端侧自回归 decode 阶段完全受限于内存带宽。在 1 TFLOP/s 算力下, 1B 参数模型生成单个 token 的算术耗时仅为 2 ms, 而以 25 GB/s 带宽搬运 FP16 权重与 KV cache 则需 88.053 ms。
roofline 模型指出单步执行耗时取决于以下两项物理下界中的较慢者:
- 计算单元完成全部乘加运算所需的时间。
- 从内存读取全部所需张量传输至计算单元所需的时间。
decode 阶段逐个生成 token, 每步每个参数约执行一次乘法与一次加法, 合计约 20 亿次浮点运算, 在 1 TFLOP/s 算力下仅需 2 ms; 但每步都必须将全量权重与历史 KV cache 从内存读取一遍, FP16 下总搬运量约 2.2 GB, 按 25 GB/s 带宽计算耗时达 88.053 ms, 因此系统瓶颈落在带宽而非算力。
再按功率乘以时间估算单步能耗, 6 W 整机功耗下 FP16 单 token 能耗为 0.52832 J; INT4 量化后冷启动单 token 延迟降至 28.053 ms, 而热降频使持续带宽减半后延迟升至 56.106 ms, 说明冷启动短时峰值无法代表持续运行十分钟后的稳态速度。

软硬件联合设计从目标任务质量与端侧物理约束出发协同选定模型宽深比、量化位宽、编译器内存布局与底层算子内核, 理论压缩比必须有对应内核支持才能兑现加速。联合设计要求将模型结构与目标硬件作为一个整体优化, 而非先离线训练大模型再强行裁剪部署:
1. 先明确业务质量底线及目标设备的内存、带宽与散热功耗上限。
2. 再联合决策网络层宽与层深、权重量化位宽、张量内存排布及算子内核实现。
若目标硬件缺乏原生低比特 (如 INT4) 矩阵乘内核, 运行时必须先将低比特权重反量化回高位宽再执行计算, 本例简化预算模型并未计入这笔反量化解码开销。此外整机电池续航还受其他并发负载与电源效率影响: 本例假设的 6 W 代表整机功耗模型, 实际运行中的屏幕背光、蜂窝网络通信与电源转换损耗均会改变真实续航表现。

Green AI 能效评估必须综合报告单次成功任务总能耗、硬件有效利用率、失败重试开销与设备生命周期摊销假设, 不能仅报单 token 静态能耗。全面衡量端侧与云端 AI 系统的真实能源消耗需纳入三项系统损耗:
- 生成失败或验证不过引发的多次重试, 其累计能耗必须分摊至最终成功的任务上。
- 低硬件利用率意味着大量静态功耗消耗在等待与空转期间。
- 生命周期核算需明确硬件制造碳足迹与服役年限的分摊口径。
更低的瞬时运行功率并不必然带来更低的总能耗: 单步能耗等于功率乘以耗时, 热降频后若执行耗时增长幅度超过功率下降幅度, 单 token 能耗反而上升。本例在热降频情形下仅将带宽减半而保持 6 W 功耗假设不变, 耗时翻倍导致单 token 能耗从 0.16832 J 翻倍至 0.33664 J; 真实设备降频时电压与功耗也会同步变化, 必须依赖真机功率计实测, 脱离实测数据不得作出碳排放或电池续航承诺。

## 怎样验证

实验将硬件与模型规格全部显式固定为公开假设 (1B 参数规模、2 GiB 内存上限、25 GB/s 内存带宽、1 TFLOP/s 峰值算力、6 W 系统功耗), 依次切换 FP16、INT4 与 INT4 热降频三种受控情形, 横向对比总内存可装载性、单 token 毫秒延迟与单 token 焦耳能耗。
三种情形遵循单变量对照原则:
- FP16 与 INT4 之间仅改变每个权重参数的存储位宽。
- 热降频情形在 INT4 基础上仅将有效内存带宽减半。
验收判定依次核查总内存是否控制在 2 GiB 以内, 并对比各情形下的延迟与能耗读数。该代价模型不替代真机评测, 实际工程选型仍需在目标设备上实测量化精度损失、壳温变化、动态功率曲线与真实电池放电表现。

## 与真实系统的差距

预算模型，不是手机或芯片跑分，不提供特定设备续航承诺。真实能耗需扣除/报告空闲基线并说明测量边界。

## 常见误区与自测

权重从 FP16 改 INT4, 峰值内存一定降为四分之一吗?

<details><summary>展开解析</summary>

不一定。权重量化仅按位宽比例缩减模型参数体积 (本例从 1907.35 MiB 降至 476.84 MiB), 而 192 MiB 的 KV cache 与 256 MiB 的运行时开销保持不变, 因此总峰值内存仅从 2355.35 MiB 降至 924.84 MiB, 远未降到原来的四分之一。
将总内存拆分为三个独立分项即可看清原因:
- FP16 每参数占 16 位, INT4 每参数占 4 位, 只有静态权重这一项严格缩减为原来的四分之一。
- KV cache 存储推理阶段动态生成的上下文 K、V 张量, 默认仍以 16 位精度驻留内存, 不随权重位宽自动压缩。
- 推理引擎自身的 256 MiB 运行时固定开销同样与权重位宽无关。
若总内存严格降至四分之一应约为 589 MiB, 而实算总占用为 924.84 MiB, 约为原总量的 39%; 随着上下文序列进一步拉长, KV cache 占比持续上升, 整体压缩比还会离四分之一更远。

</details>
