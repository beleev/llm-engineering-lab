# 多租户调度: 总体吞吐会掩盖谁的等待

A 连发 60 条长请求, B 每 15 tick 发一条短请求。FIFO 下 B 的 4 条只完成 1 条, 首次等待 25 tick; 固定优先级 (A 高优) 下 B 完成 0、超时 4; 公平轮转让 B 4 条全完成、首次等待 0; 再加每租户配额 8, A 的队列峰值从 40 降到 8, 换来 41 条拒绝。四种策略的请求终态总数都是 64, 总吞吐看不出谁在饿, 要按租户看等待、超时和 goodput。

## 怎么跑

```bash
python -m llm_infer.m33_tenant_scheduling.demo
```

## 先看这几件事

- 全局队列容量限制的是总资源, 租户配额限制的是单个调用方的占用, 两者不是同一个约束: 公平轮转下 A 的队列峰值仍是 40, 加配额 8 之后才降到 8。固定优先级在持续高优负载下会饿死其他请求, 本例 B 完成 0、超时 4。
- 公平轮转按等成本的服务量子轮流分配机会: 长请求没跑完就回自己租户的队首, 不挡另一租户拿下一个量子, B 的首次等待从 25 tick 降到 0。真实 token 的代价不相同, 要结合 prefill/decode、KV 和预算来估。
- goodput 按租户统计端到端延迟不超过 10 tick 的完成数, 再除以含排空期的观测时长 (100 或 97 tick); 同时报告超时、拒绝和队列峰值。首次获得服务的样本才有等待读数, 有限轨迹也不证明任意负载下公平。

## 怎样验证

固定两租户的同一条到达轨迹 (A 60 条长请求、B 4 条短请求), 比较 FIFO、固定优先级、公平轮转、公平与配额四种策略; 判定看请求终态是否守恒为 64、B 的完成数、A 的队列峰值是否不超过 8, 以及每租户的 goodput。
