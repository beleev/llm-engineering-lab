# 多租户调度：总体吞吐会掩盖谁的等待

连续的大租户请求可能让小租户长期等不到服务。按租户看等待、超时和 goodput，才能发现总吞吐藏住的问题。

## 怎么跑

```bash
python -m llm_infer.m33_tenant_scheduling.demo
```

## 先看这几件事

- 全局队列容量限制总资源；租户配额限制单个调用方的占用，两者不是同一个约束。固定优先级在持续高优先级负载下可能饿死其他请求。
- 公平轮转以等成本服务量子分配机会；长请求在自己的租户队列继续，不阻止另一租户获得一个量子。真实 token 的代价不相同，需结合 prefill/decode、KV 和预算估计。
- goodput 按租户统计满足端到端 SLO 的完成数，并除以包含排空期的观测时间；同时报告超时、拒绝与队列峰值。有限轨迹的结果不证明任意负载下公平。

## 怎样验证

固定两租户到达轨迹，比较 FIFO、固定优先级、公平轮转和配额；核对请求终态守恒、B 租户完成数、A 队列上限及每租户 goodput。
