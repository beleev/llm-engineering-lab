# 多租户调度: 总体吞吐会掩盖谁的等待

这组实验模拟一台每个 tick (模拟里的时间单位) 只能做 1 份工作的服务器, 同时服务两个租户 (共用这台服务器的两家客户)。A 从第 0 tick 起每个 tick 发一条长请求, 共 60 条, 每条要 5 份工作; B 每 15 tick 发一条短请求, 共 4 条, 每条要 2 份工作。所有请求排一条队、先来先服务 (FIFO) 时, B 的 4 条只完成 1 条, 第一次被服务前等了 25 tick; 固定优先级让 A 优先时, B 完成 0 条、超时 4 条; 公平轮转让两家轮流各拿 1 tick, B 的 4 条全部完成, 首次等待 0; 再给每家加一个排队上限 8 (配额), A 的队列峰值从 40 降到 8, 代价是 A 有 41 条被拒绝。四种策略下请求的最终状态都是 64 条, 只看总数看不出谁在挨饿, 要按租户分别看等待、超时和 goodput (满足延迟要求的完成数)。

## 怎么跑

```bash
python -m llm_infer.m33_tenant_scheduling.demo
```

## 先看这几件事

- 全局队列容量和租户配额管的不是一件事。全局容量限制的是整台服务器一共能排多少请求; 租户配额限制的是某一家最多能占多少, 防止一家把队列塞满。公平轮转下 A 的队列峰值仍是 40, 因为轮转只管谁先被服务, 不管谁能排进来; 加上每家最多排 8 条的配额后, 峰值才降到 8。固定优先级是另一种失败: 只要高优先级的 A 一直有请求在排, 低优先级的 B 就永远轮不到, 本例 B 完成 0 条、超时 4 条, 这种情况叫饿死。
- 公平轮转按等成本的服务量子分配机会: 每个 tick 轮到下一家租户, 它队首的请求被服务 1 tick (一个量子), 不管这条请求总共要多少份工作。长请求没做完就放回自己租户的队首, 等下次轮到再继续, 不会一直占着服务器挡住另一家。所以 B 的请求不用排在 A 的长请求后面, 首次等待从 FIFO 下的 25 tick 降到 0。真实 LLM 请求里每个 token 的代价并不相同, 一个量子值多少, 要结合 prefill (一次性处理整段输入) 和 decode (一个一个生成输出)、KV cache (生成时缓存的中间结果) 的占用和预算来估。
- goodput 按租户统计: 只数端到端延迟 (从到达到完成) 不超过 10 tick 的完成请求, 再除以观测时长。观测时长包含所有请求排空的时间, 所以是 100 tick, 加配额那组提前排空, 是 97 tick。只报 goodput 不够, 还要同时报超时、拒绝和队列峰值。首次等待只能从真正被服务过的请求里统计: 固定优先级下 B 一条都没被服务, 等待读数是空的 (网页上显示为「不适用」), 不代表等待为 0; 而且一条固定的到达轨迹, 也证明不了任意负载下都公平。

## 怎样验证

固定两个租户的同一条到达轨迹 (A 60 条长请求、B 4 条短请求), 每条请求从到达起超过 40 tick 还没完成就算超时, 比较先进先出、固定优先级、公平轮转、公平加配额四种策略。判定看四件事: 每种策略下完成、超时、拒绝加起来是否正好 64 条, B 完成了几条, A 的队列峰值是否不超过 8, 以及每个租户的 goodput。
