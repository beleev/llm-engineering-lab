# 多租户调度: 总体吞吐会掩盖谁的等待

本组实验通过离散事件仿真模拟一台每 tick (仿真时间步) 仅能完成 1 单位计算量的共享推理服务器, 同时承载两个租户的不对称流量:
- 租户 A: 自第 0 tick 起每 tick 连续提交 1 条长请求, 共 60 条, 每条需 5 单位计算量。
- 租户 B: 每隔 15 tick 提交 1 条短请求, 共 4 条, 每条仅需 2 单位计算量。

对比四种调度与准入策略的运行结果:
- 全局先进先出 (FIFO): 所有请求混入单一队列按到达次序服务, 租户 B 的 4 条请求仅完成 1 条, 首次获得服务前排队等待达 25 tick。
- 静态固定优先级: 将租户 A 设为高优先级后, 租户 B 完成 0 条、全部 4 条超时。
- 按租户公平轮转: 两家租户交替各获 1 tick 服务量子, 租户 B 的 4 条短请求全部按时完成, 首次等待降至 0。
- 公平轮转叠加租户配额: 为每个租户增设排队上限 8 后, 租户 A 的队列积压峰值从 40 降至 8, 超出配额的 41 条请求在入口即被快速拒绝。

四种策略处理的请求终态总数均为 64 条, 仅看全局汇总指标无法识别局部排队饥饿, 必须分租户独立统计首次等待时间、超时率与 goodput (在延迟 SLO 内成功完成的请求吞吐)。

## 怎么跑

```bash
python -m llm_infer.m33_tenant_scheduling.demo
```

## 先看这几件事

- 全局队列容量上限与单租户配额分别约束系统总内存水位与跨租户故障隔离, 二者不能相互替代:
- 全局队列容量: 限制整台服务器允许驻留等待的请求总数上限, 保护宿主进程不被突发流量冲垮。
- 单租户配额: 限制单个调用方最多允许占用的排队槽位数, 防止高压噪声邻居独占共享缓冲池。

纯公平轮转策略仅改变出队服务次序而不限制入队准入, 因此租户 A 的队列峰值仍高达 40; 叠加每租户最多排队 8 条的准入配额后, 峰值才受控收敛至 8。静态固定优先级则暴露出另一类典型失效: 只要高优先级租户 A 持续有在途请求, 低优先级租户 B 便永远无法获得调度机会, 本实验中 B 完成 0 条、超时 4 条, 即发生调度饥饿。
- 按租户公平轮转通过细粒度服务量子切分消除长请求造成的跨租户队头阻塞:
1. 调度器在每个 tick 轮询切换至下一个非空租户队列。
2. 为当前选中租户的队首请求分配 1 tick 计算时间片 (即一个服务量子), 无论该请求剩余总工作量大小。
3. 单次量子内未执行完毕的长请求保留剩余工作量并放回所属租户队首, 等待下一轮调度继续推进, 不会持续独占执行单元阻塞其他租户。

借此机制, 租户 B 的短请求无需排在租户 A 积压的长请求队列末尾等待, 其首次获服务等待时间从全局 FIFO 下的 25 tick 直接降至 0。实验边界: 真实 LLM 推理服务中不同阶段的计算与显存成本并不均匀, 工程上定义公平配额量子时必须联合折算 prefill 计算量、decode 迭代步数以及驻留 KV cache 的显存占用预算。
- 多租户服务质量评估必须分租户统计满足延迟 SLO 的有效吞吐 (goodput), 并同步披露超时、准入拒绝与队列峰值指标。本实验中 goodput 定义为端到端延迟 (从请求到达到执行完成) 不超过 10 tick 的完成请求数除以完整排空观测时长: 前三种策略排空总时长为 100 tick, 叠加配额组因入口拒绝了超额积压请求而在 97 tick 提前排空。统计首次等待时间时必须仅对实际获得过服务的请求求取: 静态优先级下租户 B 无任何请求获得调度, 该项读数为空值 (前端面板展示为「不适用」), 绝不能误记为等待 0 tick。实验边界: 基于单条确定性到达轨迹的仿真结果仅展示各机制的典型行为差异, 不能外推证明调度器在任意随机流量分布下均满足公平性。

## 怎样验证

固定双租户的同一条确定性请求到达轨迹 (租户 A 连续提交 60 条长请求, 租户 B 间隔提交 4 条短请求), 统一设定请求自到达起逾 40 tick 未完成即判定超时, 横向对比全局 FIFO、静态固定优先级、按租户公平轮转与公平轮转加配额四种策略。验收联合核查四项指标:
- 守恒校验: 每种策略下的完成数、超时数与准入拒绝数之和是否严格等于总请求数 64。
- 低频租户保障: 租户 B 成功完成的请求条数。
- 资源隔离水位: 启用配额后租户 A 的队列积压峰值是否严格不超过 8。
- 有效服务产出: 各租户独立计算的 goodput 读数。
