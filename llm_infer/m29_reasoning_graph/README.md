# 推理图: 链、树、合并与逐步核验

## 直觉

从 1 用「加一 / 翻倍」走到 15: 贪心链每步只选翻倍, 4 步就越过目标, 失败; 树搜索找到 [1, 2, 3, 6, 7, 14, 15], 展开 54 个状态; 图按状态去重, 同一条路只展开 14 个。多写几步不一定更会推理: 搜索改善的是候选空间和验证机会, 前提是状态和验证器定义正确。

## 核心原理

CoT 提示只是请求模型输出中间步骤; CoT 监督训练改变参数分布; RL 依据奖励更新策略。三者的输出都带解释, 不能因此混为一谈。

树保留不同路径, 图合并等价状态; 本例从 1 用加一/翻倍到 15, 比较贪心、广度搜索和去重后的广度搜索, 展开数 4 / 54 / 14。合并键必须包含影响未来的完整状态; 有预算、权限或历史约束时, 只按当前数值合并会出错。

最终答案对不代表过程对, 独立验证器逐边检查每一步是不是合法动作。本例构造了 [1, 2, 7, 15]: 终点正确, 2→7 不是合法变换, 验证器拒绝, 这就是 outcome-only 评分的 overcredit。外部解释能验证, 也不证明它忠实描述了模型内部因果。

测试时预算要算上生成、评分器前向、工具、重试和等待。相同生成 token 不等于相同总成本; 要比较 pass@k、每次成功的成本、尾延迟和验证器漏判。

## 怎样验证

三个策略用同一个初态 1、目标 15 和动作集合 {+1, ×2}, 上限 80 次展开, 统计是否成功和展开状态数, 并用同一个验证器拒绝伪造路径; 迁移到 LLM 后还要审计步骤粒度、验证器的相关错误和未见任务的泛化。

## 与真实系统的差距

有限整数状态搜索，不是完整 ToT/GoT 论文复现。检验文本步骤只检验外部一致性，内部因果忠实性需激活干预等独立证据。

## 常见误区与自测

两条路径到达同一数字, 就一定能合并吗?

<details><summary>展开解析</summary>

不一定。本例能合并, 是因为状态只有一个整数; 剩余预算、动作历史、权限这些会影响未来可行解的东西一旦进来, 只用表面数字作键就会错。

</details>
