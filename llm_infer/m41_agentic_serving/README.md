# m41 — Agent 负载下的推理服务: 思考 token、工具停顿与前缀命中

[llm_infer 目录](../README.md) · [交互实验](https://beleev.github.io/llm-engineering-lab/#/infer/agentic-serving)

## 直觉

推理模型每次调用先写一段思考 (thinking), 再给出工具调用或回答; Agent 完成一个任务要来回调用很多次工具。对服务端来说, 这带来四个变化:
- 输出以思考 token 为主。思考 token 和可见输出一样要一个一个 decode, 一样占 KV。
- 每次调用的 prompt 都是「整段历史 + 新的工具结果」, 前缀缓存能省下大部分 prefill。前提是历史没被改过: 如果下一次请求把上一轮的思考块删了, 被删位置之后的 token 全部对不上缓存, 要重算。
- 两次调用之间, 会话停在工具上等结果, 可能是 1 秒的检索, 也可能是 1 分钟的测试。这期间这条会话的 KV 留着就占显存, 丢掉的话回来要整段重算。
- 思考预算 (effort) 让输出变长: 单请求延迟随之线性变长, 集群吞吐却掉得更快, 因为每个请求的 KV 变大, 能同时跑的请求变少了。

本模块的数字全部来自代价模型和离散事件模拟, 是估算, 不是实测。

## 核心原理

### 核心数据结构或公式

```
[1] 历史拼法 (render)
  keep_all          历史里的思考块全部保留
  strip_on_user     新的用户消息到来时删掉之前各轮的思考, 当前工具循环里的保留 (Qwen3 / DeepSeek-V3.2 的对话模板)
  strip_all         每次请求都删掉之前的思考
  命中 = 本次 prompt 与之前任何一次完整序列 (prompt + 解码出的 token) 的最长公共前缀, 逐 token 比较得出

[2] effort (DecodeCost)
  一步解码耗时 = 读一遍权重 (8 ms) + 批里所有上下文 × 每 token KV 字节 ÷ 显存带宽
  单请求延迟    = prompt ÷ prefill 速度 + 输出长度 × 一步耗时 (批大小 1)
  最大并发 B    = KV 池 ÷ (prompt + 输出)              ← 按最长上下文预留
  集群请求/s    = B ÷ 一步耗时(B) ÷ 输出长度  ∝  1 / (输出 · (prompt + 输出))   (权重读取占主导时)

[3] 工具停顿 (simulate): KV 池 + 16 个并发槽 + 一条共享的 prefill 队列
  evict    停顿时 KV 留在池里, 随时可淘汰 (LRU)         = 引擎默认的前缀缓存
  pin      钉住到会话回来                                池子钉满、又没有调用在跑时只能被迫淘汰
  ttl      停顿后钉住 8 s, 过期变成可淘汰
  hint     应用告诉引擎这次是快工具还是慢工具: 快的 TTL = 2 × 快工具中位耗时, 慢的不钉、优先淘汰
  被淘汰的会话回来时, 整段历史重新 prefill, 和别的调用排同一条 prefill 队
```

读代码时盯住两处:
1. render 里 `turn < cur_turn` 那一行: 思考块什么时候被跳过, 决定公共前缀断在哪。
2. simulate 里 free() 的排序和 pinned_until: 先淘汰谁、钉住多久。

- [2] 输出变长 40.7 倍, 单请求延迟变长 42.8 倍 (上下文变长后每步读的 KV 也多了一点), 集群请求吞吐降到 1/229: 并发从 62 降到 8, 每个请求的输出又长了 40 倍。

## 与真实系统的差距

- 历史拼法是各家对话模板和 API 规定的, 不由引擎决定:
  - Qwen3 的模型卡写明多轮对话的历史输出只保留最终回答、不带思考内容, 对话模板只给最后一条真正的用户消息之后的 assistant 消息渲染思考。
  - DeepSeek-V3.2 的编码代码默认在最后一条用户消息之前删掉 reasoning_content。DeepSeek 现行 API 文档的规定则分情况: 不带 tools 时上一轮的 reasoning_content 会被忽略; 带 tools 时所有历史轮次的 reasoning_content 都要传回并拼进上下文, 不传回会返回 400。
  - Anthropic 的文档要求在一个工具循环内把思考块原样传回。Claude Opus 4.5 及之后的 Opus、Sonnet 4.6 及之后的 Sonnet 和 Haiku 5.5 默认保留之前所有轮次的思考块; 更早的模型在收到不是工具结果的用户消息时自动删掉之前的思考块, prompt caching 文档写明这时这些思考块之后的消息都会从缓存里移除。文档还说保留的思考块能让工具调用期间命中缓存。
  - OpenAI 的 Responses API 要求在工具调用之后把推理项 (reasoning items) 和工具输出一起传回, 并用 reasoning.context (current_turn / all_turns / auto) 控制保留几轮。
- 删思考块对答题质量的影响 (模型看不到自己之前的推理) 不在模拟范围内; 删与不删只比较 KV 和重算。
- 工具停顿期间的 KV 保留: Continuum (arXiv 2511.02230) 对产生工具调用的请求把 KV 钉在 GPU 上, TTL 由重新加载的代价和淘汰可能带来的排队延迟决定, 配合按程序 (整个 Agent 任务) 先到先服务的调度, 论文报告平均任务完成时间改善 8 倍以上。这里的 hint 策略只用了「快工具 / 慢工具」两档提示, 没有按重算代价算 TTL。
- 另一条路是让应用直接编辑缓存: Leyline (arXiv 2606.01065) 让应用下指令删掉或替换缓存里的一段 (比如失败的工具调用、过时的输出), 用 RoPE 旋转的闭式校正修正后面 token 的位置, 不用把后面全部重新 prefill, 摘要报告回放时缓存命中提高 11.2 个百分点、延迟最多减少 241 ms。论文附录里还列了钉住、按工具链衰减、淘汰思考片段之类的保留指令, 原文写明这些还没有实验验证。被删片段之后的 token 当初是看着那段内容算出 K/V 的, 只校正位置并不会让它们回到「没见过那段内容」的样子。
- 托管 API 的前缀缓存也有寿命: Anthropic 默认 5 分钟、可选 1 小时, 文档建议思考很长的任务考虑 1 小时。
- 代价模型很粗: 解码每 token 时间不随批大小变 ([3]), 一步耗时只算读权重和读 KV ([2]), prefill 用固定的 8000 tok/s, 不建模 prefill 和 decode 抢同一块 GPU、也不建模 CPU 卸载 (m20)。会话之间不共享前缀, 工具耗时是对数正态分布的合成数据。

## 常见误区

- 「删掉历史里的思考块能省显存, 没有别的代价」: 删掉就是改了历史, 断点之后的 token 都要重算 ([1]: 第 2 轮第一次调用命中率 99% → 31%)。省显存和省重算要一起算。
- 「命中率越高越好」: 要看要算的 token 绝对数。每次都删思考的命中率比全部保留低, 要算的 token 只多 11%, 上下文却短了一半多。
- 「effort 调高一档, 吞吐降一档」: 显存约束下并发同时变少, 集群请求吞吐下降得比输出变长快得多 ([2]: 输出 ×40.7, 请求吞吐 ÷229)。
- 「工具调用期间把 KV 钉住最保险」: 钉住的会话占满池子后, 新调用排长队, 最后还是要被迫淘汰 ([3]: 平均 TTFT 277.9 s)。按工具快慢区别对待才同时省下重算和排队。

## 自测题

1. 一个 Agent 第 1 轮调用了 5 次工具, 每次思考 1200 token。第 2 轮的用户消息到来时, 对话模板删掉了第 1 轮的所有思考。引擎前缀缓存最多能命中到哪里?
   **答**: 命中到第 1 轮第一次调用的思考块之前 (system prompt + 第 1 轮用户消息)。第一个被删的思考块之后, 新 prompt 和缓存里的序列逐 token 对不上了, 后面的工具调用、工具结果和回答都要重算。
2. KV 池固定, 思考预算从 2048 提到 8192 token, 为什么集群每秒完成的请求数降得比 4 倍还多?
   **答**: 每个请求要算的输出多了约 3.6 倍; 同时每个请求预留的 KV 也变大, 能同时跑的请求从 47 个降到 24 个, 每秒产出的 token 也少了。两个因素相乘, 请求吞吐降到约 1/6。
3. 工具调用期间, 为什么 LRU 淘汰并不算太差, 而「全部钉住」反而最差?
   **答**: LRU 先淘汰停得最久的会话, 停得久的多半是慢工具, 本来就该让出显存; 全部钉住时慢工具会话占着池子不放, 新调用进不来, 池子满了只能被迫淘汰, 排队和重算两头都没省下。
