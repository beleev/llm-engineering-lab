# 剪枝与融合: 零值不等于少做计算

## 直觉

这组实验用一个 32×16 的输入乘一个 16×8 的权重矩阵, 比较几种剪枝做法实际省下了多少计算。权重矩阵每一行对应一个输入通道 (输入向量的一个维度), demo 把后 8 行故意缩小到 0.001 倍, 让这 8 个通道几乎没有贡献。
两种做法的乘加次数:
- 把 16×8 权重里一半置零, 非零数从 128 降到 64, 但普通稠密矩阵乘 (dense GEMM, 不管值是不是 0 都逐个相乘相加) 的乘加仍是 4096 次。
- 真的删掉 8 个输入通道, 矩阵变小, 乘加才降到 2048。
两种做法去掉的恰好是同一批小权重, 所以输出 MSE (剪枝后输出和原输出逐元素之差的平方平均) 同样是 7e-06。权重变成零, 稠密矩阵乘照算; 想加速, 要让执行器真的跳过这些工作。

## 核心原理

非结构化剪枝把小权重置零; 只要仍走 dense GEMM, 算子形状和 MAC 数都不变, 本例 64 个非零仍算 4096 次。非结构化剪枝是一个一个挑权重, 不管它在矩阵里的什么位置, 本例挑的是绝对值排在后一半的 64 个。dense GEMM 按矩阵形状干活: 32×16 的输入乘 16×8 的权重, 每个输出元素要做 16 次乘加, 32×8 个输出共 4096 次 MAC (multiply-accumulate, 一次乘法加一次累加)。权重里的 0 照样被乘、被加, 只是结果是 0, 所以一次都没省。
结构化剪枝按行范数删掉整个输入通道: 行范数是一行所有权重合起来的大小, demo 删掉范数低于中位数的 8 行, 同时去掉输入里对应的 8 列, 矩阵从 16×8 变成 8×8, 普通 dense 实现里运算才减半, 降到 2048 次。

本例把后 8 个通道的权重缩到 0.001 倍造出低贡献通道, 断言掩码输出和压缩矩阵输出一致, 并报告相对 dense 的误差 7e-06。
断言比较的两种输出:
- 掩码输出是指矩阵保持 16×8 不变, 只把被删的行乘 0 再算。
- 压缩矩阵输出是指真的拿掉这些行和输入里对应的列, 用 8×8 的小矩阵算。
demo 断言两者相等, 说明删通道没有改变数学结果, 只是不再做乘 0 的那部分。7e-06 是剪枝后输出和原始稠密输出的 MSE, 它很小, 因为删掉的权重本来就只有正常权重的千分之一大。
硬件稀疏格式还要求模式、索引和内核支持; 密度不够低时, 省下的乘加会被索引开销吃掉: 稀疏格式要额外存每个非零值的位置, 计算时先查位置再取数, 非零还很多时, 查位置的花费可能比省下的乘法还多。

融合把 bias、激活、残差这些中间结果留在寄存器或片上存储。本例 add→ReLU→scale 三个逐元素算子分开跑要读写 12288 字节, 融合后理想是 4096 字节。逐元素算子对张量的每个位置单独做同一种运算, 本例先加 bias, 再过 ReLU (负数变 0), 再乘 scale。矩阵乘的输出是 32×8 个 float64, 占 2048 字节。
两种跑法的读写量:
- 三个算子分开跑时, 每个都要从内存读一次输入、写一次结果, 共 3 次读加 3 次写, 2048 × 6 = 12288 字节。
- 合成一个算子后, 只读一次原始输出、写一次最终结果, 2048 × 2 = 4096 字节, 中间结果不落回内存 (bias 和 scale 各只有 8 个数, 没算进去)。
demo 在 numpy 里只核对两种写法数学上相等, 字节数是按这个规则算的理想值, 不是测出来的。
编译器还要处理形状、布局与数值约束; CUDA Graph 只复用提交调度, 不自动等于算子融合: CUDA Graph 把一串 GPU 调用录下来整体重放, 省的是 CPU 一次次发起调用的开销, 每个算子仍然各自读写内存。

压缩验收不能只测平均困惑度: 要分别测低频实体、长推理、多语言、安全边界、校准和拒答。困惑度 (perplexity) 衡量模型对测试文本有多意外, 越低越好, 但它是对大量文本取平均, 少数情况变差会被平均值摊薄, 看不出来。
所以要单独测这些少数情况:
- 很少出现的人名地名。
- 要连续推好几步的问题。
- 训练数据少的语言。
- 该拒绝的危险请求。
校准是看模型说有八成把握时是不是真的大约八成答对。
相同吞吐下质量变差, 要报告质量—延迟的 Pareto 取舍: 把每个压缩方案的质量和延迟放在一起比, 列出那些想再快就必须更差的方案, 让使用者自己选。本例只看输出 MSE, demo 的说明也写明模型压缩还需看长尾、推理、安全切片。

## 怎样验证

固定同一个 32×16 输入和 16×8 权重, 比较稠密、权重置零、删除通道三种模式的非零权重数、dense 乘加次数和输出 MSE, 再按理想访存算未融合与融合的字节数。判定看两件事: 乘加次数有没有变少, 输出 MSE 是否仍然很小; 字节数只说明融合在理论上能省多少读写。
这里没有 GPU kernel 和真实加速比, 实测要 warm-up、同步、固定 batch/上下文、设备功率与分位数:
1. 先空跑几轮让设备状态稳定。
2. 计时前等 GPU 算完。
3. 固定 batch 和上下文长度。
4. 记录设备功率。
5. 报告延迟的分位数而不只是平均值。

## 与真实系统的差距

numpy 的通道裁剪与理论流量。没有稀疏 GPU kernel 或融合 kernel 的实测加速；模型压缩还需看长尾、推理、安全切片。

## 常见误区与自测

把 90% 权重置零后, dense GEMM 会自动快十倍吗?

<details><summary>展开解析</summary>

不会。零值只改变数值, 本例置零一半后乘加仍是 4096 次。原因是 dense GEMM 按矩阵形状安排计算: 16×8 的权重里不管有多少个 0, 每个输出元素都要做 16 次乘加, 乘 0 和乘别的数一样要做一遍。
要少做工作, 有两条路:
- 删掉整个维度 (本例乘加降到 2048), 让矩阵本身变小。
- 用支持相应稀疏格式的算子, 只存非零值和位置, 跳过 0 的乘法。
后一条还要硬件和内核支持, 而且非零比例要足够低, 否则查位置的开销会吃掉省下的乘法。
