# 剪枝与融合: 零值不等于少做计算

## 直觉

把 16×8 权重里一半置零, 非零数从 128 降到 64, dense GEMM 的乘加仍是 4096 次; 真的删掉 8 个输入通道, 乘加才降到 2048, 输出 MSE 同样是 7e-06。权重变成零, 稠密矩阵乘照算; 想加速, 要让执行器真的跳过这些工作。

## 核心原理

非结构化剪枝把小权重置零; 只要仍走 dense GEMM, 算子形状和 MAC 数都不变, 本例 64 个非零仍算 4096 次。结构化剪枝按行范数删掉整个输入通道, 矩阵从 16×8 变成 8×8, 普通 dense 实现里运算才真的减半。

本例把后 8 个通道的权重缩到 0.001 倍造出低贡献通道, 断言掩码输出和压缩矩阵输出一致, 并报告相对 dense 的误差 7e-06。硬件稀疏格式还要求模式、索引和内核支持; 密度不够低时, 省下的乘加会被索引开销吃掉。

融合把 bias、激活、残差这些中间结果留在寄存器或片上存储: 本例 add→ReLU→scale 三个逐元素算子分开跑要读写 12288 字节, 融合后理想是 4096 字节。编译器还要处理形状、布局与数值约束; CUDA Graph 只复用提交调度, 不自动等于算子融合。

压缩验收不能只测平均困惑度: 要分别测低频实体、长推理、多语言、安全边界、校准和拒答。相同吞吐下质量变差, 要报告质量—延迟的 Pareto 取舍。

## 怎样验证

固定同一个 32×16 输入和 16×8 权重, 比较稠密、权重置零、删除通道三种模式的非零权重数、dense 乘加次数和输出 MSE, 再按理想访存算未融合与融合的字节数; 这里没有 GPU kernel 和真实加速比, 实测要 warm-up、同步、固定 batch/上下文、设备功率与分位数。

## 与真实系统的差距

numpy 的通道裁剪与理论流量。没有稀疏 GPU kernel 或融合 kernel 的实测加速；模型压缩还需看长尾、推理、安全切片。

## 常见误区与自测

把 90% 权重置零后, dense GEMM 会自动快十倍吗?

<details><summary>展开解析</summary>

不会。零值只改变数值, 本例置零一半后乘加仍是 4096 次。要少做工作, 得删掉整个维度 (本例乘加降到 2048), 或者用支持相应稀疏格式的算子。

</details>
