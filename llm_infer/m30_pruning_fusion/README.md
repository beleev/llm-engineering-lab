# 剪枝与融合: 零值不等于少做计算

## 直觉

本实验使用 32×16 的输入矩阵乘以 16×8 的权重矩阵, 对比非结构化置零与结构化通道裁剪实际节省的计算量。权重矩阵的每一行对应一个输入通道, 实验预先将后 8 行权重缩放至 0.001 倍以构造低贡献通道。
两种剪枝方式在普通稠密矩阵乘 (dense GEMM) 下的乘加次数差异显著:
- 非结构化置零将 16×8 权重中幅值较小的一半元素设为 0, 非零元素数从 128 降至 64, 但 dense GEMM 按固定张量形状逐元素执行乘加, 运算量仍为 4096 次。
- 结构化剪枝直接移除后 8 个输入通道及对应输入列, 权重矩阵收缩为 8×8, 乘加次数随之减半至 2048 次。
由于两种方案移除的恰好是同一批低幅值权重, 剪枝输出相对于原始稠密输出的 MSE 均为 7e-06。将权重置零并不会让稠密算子自动提速, 只有缩减张量形状或改用支持稀疏跳过的底层内核才能真正减少执行工作量。

## 核心原理

非结构化剪枝仅将低幅值权重置零而不改变张量形状, 只要执行路径仍走 dense GEMM, 算子形状与乘加次数便保持不变, 本例保留 64 个非零权重仍需执行 4096 次乘加。非结构化剪枝脱离矩阵行列结构逐元素筛选权重, 本例将绝对值排在后一半的 64 个元素置为 0。然而 dense GEMM 严格按张量维度调度指令: 32×16 的输入乘以 16×8 的权重时, 每个输出位置固定执行 16 次 MAC (multiply-accumulate, 乘加运算), 32×8 个输出元素合计固定消耗 4096 次 MAC, 值为 0 的权重依然参与硬件乘法与累加。
结构化剪枝则以整行或整列为单位裁剪整个通道: 本例计算权重矩阵每行的范数, 直接剔除行范数低于中位数的 8 行, 并同步裁掉输入矩阵对应的 8 列, 使权重形状从 16×8 压缩为 8×8, 在标准 dense 算子下直接将运算量减半至 2048 次。

实验将后 8 个输入通道的权重缩放至 0.001 倍以构造低贡献通道, 断言零掩码输出与压缩矩阵输出严格一致, 并测得相对于原始稠密输出的 MSE 为 7e-06。
代码断言对齐了两种等价实现路径:
- 零掩码输出保持 16×8 权重形状不变, 仅将被裁剪行乘以 0 后执行矩阵乘。
- 压缩矩阵输出直接物理移除被裁剪的 8 行及输入对应的 8 列, 以 8×8 紧凑矩阵完成计算。
两者数值结果完全一致, 证明结构化删减通道在数学上等价于消去乘 0 项, 同时省去了无效算力开销; 7e-06 的微小误差则源于被裁通道原本仅具正常通道千分之一的幅值。
若不裁剪维度而改走硬件稀疏加速, 则必须同时具备特定稀疏模式、坐标索引编码与专用稀疏内核支持; 当非零元素密度不够低时, 读取与解析位置索引的额外开销会抵消跳过零乘法所节省的时间。

算子融合将 bias、激活函数与缩放等逐元素中间结果保留在寄存器或片上缓存中, 本例将串联的 add、ReLU、scale 融合后理想主存读写量从 12288 字节降至 4096 字节。逐元素算子对张量各位置独立施加相同变换, 本例依次对矩阵乘结果加 bias、经 ReLU 将负值截断为 0、再乘以 scale。矩阵乘输出形状为 32×8 的 float64 张量, 单份占用 2048 字节。
两种执行方式的主存流量对比如下:
- 未融合分步执行时, 三个算子各自从主存读取一次输入并写回一次输出, 累计 3 次读取与 3 次写入, 理想读写总量为 $2048 \times 6 = 12288$ 字节。
- 融合为单一算子后, 仅读取一次矩阵乘输出并写回一次最终结果, 理想读写量降至 $2048 \times 2 = 4096$ 字节, 中间张量不再往返主存 (长度仅为 8 的 bias 与 scale 向量开销忽略不计)。
实验边界在于本例仅在 NumPy 中校验融合前后数值等价, 上述字节数为依据访存模型推算的理论下界而非硬件实测值。真实编译器融合还需满足张量形状、内存布局与数值精度约束; 此外 CUDA Graph 仅录制并重放 GPU 内核提交序列以省去 CPU 端发起调度的开销, 各独立算子仍会照常读写主存, 因此不等同于算子融合。

模型压缩的上线验收不能仅凭整体平均困惑度过关, 必须对低频实体、多步长推理、低资源多语言、安全边界、置信度校准与拒答行为做分切片独立评测。困惑度 (perplexity) 在大规模语料上取均值, 压缩对尾部罕见知识的损伤极易被高频常规文本摊薄掩盖。
工程验收需重点单列四类脆弱切片:
- 训练语料中出现频次较低的专有人名、地名与长尾事实。
- 依赖多步严密衔接的复杂推理任务。
- 语料占比较低的非主流语种。
- 触及安全红线、应当明确拒答的恶意请求。
同时需检验置信度校准 (例如模型给出八成把握时真实准确率是否接近八成)。若相同吞吐预算下压缩模型出现质量退化, 应完整报告质量与延迟的 Pareto 前沿曲线, 呈现不同压缩档位的显式取舍。本实验仅统计线性层输出 MSE, 代码说明亦明确指出真实模型压缩还需审计长尾、推理与安全切片。

## 怎样验证

实验固定同一组 32×16 输入张量与 16×8 权重矩阵, 横向对比原始稠密、非结构化权重置零、结构化通道裁剪三种模式下的非零权重数、dense 乘加次数与输出 MSE, 并按理想访存模型核算逐元素算子融合前后的主存读写字节数。验收同时考察乘加次数是否实质下降以及输出 MSE 是否保持低位, 访存字节数则用于刻画算子融合的理论带宽收益上界。
本实验不包含底层 GPU kernel 与真实端到端加速比测量; 真实硬件基准测试必须严格控制以下五项规程:
1. 计时前先执行多轮 warm-up 预热以稳定设备频率与缓存状态。
2. 在计时边界显式执行设备同步以等待异步 GPU 队列全部完成。
3. 固定输入 batch 规模与上下文序列长度。
4. 同步采集设备实时功耗与热状态。
5. 报告延迟分布的关键分位数而非仅报告算术平均值。

## 与真实系统的差距

numpy 的通道裁剪与理论流量。没有稀疏 GPU kernel 或融合 kernel 的实测加速；模型压缩还需看长尾、推理、安全切片。

## 常见误区与自测

把 90% 权重置零后, dense GEMM 会自动快十倍吗?

<details><summary>展开解析</summary>

不会。将权重元素置为 0 仅改变张量数值而不改变张量形状, 本例将一半权重置零后 dense GEMM 仍执行全部 4096 次乘加运算。原因在于 dense GEMM 严格按矩阵维度编排计算循环: 面对 16×8 的权重矩阵, 无论其中包含多少个 0, 每个输出位置仍固定执行 16 次乘加指令, 乘以 0 与乘以非零数消耗相同的硬件周期。
若要实质削减计算工作量, 必须采取以下两条路径之一:
- 采用结构化剪枝直接删除整个通道维度 (如本例裁剪后乘加次数降至 2048), 通过缩小稠密矩阵形状实现通用提速。
- 改用稀疏存储格式与匹配的专用稀疏算子内核, 仅存储非零元素及其位置索引并跳过零值乘法。
第二条路径不仅依赖特定硬件指令与底层内核支持, 还要求非零密度足够低, 否则索引寻址开销会抵消省下的乘加计算。
