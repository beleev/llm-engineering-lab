# 性能实测: 模型估算与 profiler 怎样对照

## 直觉

本组实验对比同一线性变换的两种等价实现:
- 分步写法 x@w+b: 先执行矩阵乘法再逐元素加上偏置 bias。
- 融合算子 torch.addmm: 在单次算子入口内联合完成矩阵乘与偏置累加。

按张量形状推导, 两种实现的逻辑 FLOPs 均为 1056768, 纸面算术运算量完全相等。然而使用 PyTorch profiler 采集底层运行事件后呈现出清晰差异:
- 矩阵乘核心算子调用次数均为 1 次。
- 底层 ATen 算子库函数调用总数为 6 次对 7 次。
- CPU 累计内存分配量为 65536 字节对 32768 字节, 分步写法因需物化矩阵乘中间张量而额外多分配了一倍内存。

理论 FLOPs 相等并不意味着真实执行耗时相等, 算子分发次数、中间缓冲区分配访存与 CPU 侧 host 调度开销必须通过实测剖析定位。

## 核心原理

严谨的性能基准测试必须将预热运行、多次独立墙钟计时与 profiler 事件追踪拆分为互不干扰的三个阶段:
1. 预热运行 (warmup): 先空跑 3 次迭代, 排除首次调用触发的算子查找、内存池初始化与缓存预热开销。
2. 独立重复计时: 连续独立测量 7 次并同时报告最小值、中位数与最大值, 反映延迟集中趋势与尾部抖动。
3. 隔离采集 profiler: 单独执行一次事件剖析以统计底层算子与内存分配, 避免 profiler 插桩本身的额外开销污染真实墙钟耗时。

报告中还须同步固定并记录 Python 与 PyTorch 版本、目标硬件设备、计算线程数 (本实验固定为单线程 1) 及重复轮数, 保证实验可复现。由于绝对耗时受宿主机硬件与系统负载影响, 墙钟时间仅保存在本地 CLI 导出的 JSON 报告中, 前端网页仅回放与机器无关的确定性事件计数。

解读 profiler 输出指标前必须明确各统计字段的精确口径, 防止误读算子计数与时间归属:
- CPU 累计分配字节: 汇总追踪区间内全部内存申请事件的字节总和 (eager 分步版为 65536 字节, fused 融合版为 32768 字节), 而非同一时刻的驻留内存峰值; 单个 128×64 的 float32 输出张量恰好占用 32768 字节, 分步版多出的 32768 字节正对应矩阵乘中间结果缓冲区。
- ATen 算子调用数: 统计全部以 aten:: 为前缀的算子分发事件 (含复合算子内部嵌套调用的子函数), 并不等同于 GPU 硬件实际启动的底层 kernel 数量; 本例中 fused 版本因内部包装分发反而多出 1 次调用 (6 对 7), 说明浅层调用计数不能直接等同于端到端快慢。
- Self 时间口径: profiler 中的 self 耗时仅统计当前事件自身扣除子调用后的独占时间, 父子嵌套事件的总耗时以及异步并行的 CPU 发射时间与 GPU 执行时间均不可直接线性相加。

异步加速卡上的延迟测量必须在计时起止边界强制执行设备同步, 否则测得的仅为主机端算子发射耗时。选做 CUDA 分支在计时前后均显式调用 synchronize 等待流队列中的全部 GPU kernel 执行完毕, 并同步采集运行期峰值已分配显存 (峰值 allocated)。若剖析链路涉及主机与设备间的异步数据传输, 还必须配合锁页内存 (pinned memory)、独立的 CUDA stream 划分及跨流事件依赖管理才能实现计算与传输重叠。实验边界: 默认离线验收仅运行单线程 CPU 分支以核验测量与事件统计流程正确, 不能据此推断真实 GPU 上的融合加速比。

## 与真实系统的差距

CPU 分配字节是正向分配事件之和，不是峰值驻留内存。profiler 会扰动耗时，计时与采样分开；CPU self 时间排除子事件但不能直接与异步 GPU 总时间相加。CUDA 选做会同步后计时并记录峰值显存；本次默认只测 CPU。

## 怎样验证

固定同一组输入张量规格 (x 为 128×64、w 为 64×64、bias 长度为 64)、单线程执行环境与确定性随机种子, 对照剖析「matmul 后加 bias」与「addmm」两种实现。验收联合核查两项标准:
- 数值等价性: 两种实现的输出张量在 1e-5 绝对容差内严格一致。
- 剖析事件一致性: 矩阵乘核心调用数、ATen 分发调用数、理论逻辑 FLOPs 与 CPU 累计分配字节数四项确定性读数均与预期基准完全吻合。

边界测试见 [test_engineering_completion.py](../../tests/test_engineering_completion.py)。

## 常见误区与自测

两种算子实现的理论逻辑 FLOPs 完全相同, 能否仅凭此认定二者的实际执行耗时相同?

<details><summary>展开解析</summary>

不能。逻辑 FLOPs 仅统计代数乘加运算次数, 完全不反映底层算子分发次数、中间缓冲区分配开销以及数据在各级存储层次间的读写搬运量。本实验中两种实现的逻辑 FLOPs 同为 1056768, 但先做矩阵乘再加 bias 的分步写法必须额外申请 32768 字节内存物化中间结果张量并再次读取累加, 且底层 ATen 算子调用数亦不相同 (6 对 7), 这些运行时开销在理论 FLOPs 公式中均不可见。规范的验证流程应分两步执行:
- 对比真实快慢时, 先执行 warmup 预热再多次独立计时统计分布。
- 定位性能差异来源时, 单独运行 profiler 逐算子核查调用与内存分配事件。

</details>
