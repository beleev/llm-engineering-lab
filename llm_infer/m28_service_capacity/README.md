# m28 · 容量不是最大并发数：看排队和好吞吐

## 直觉

接收成功不等于完成及时。到达速度超过服务能力时，请求堆在队列里，平均吞吐看似没掉，用户却在等首 token，最后超时。

## 核心原理

seed=31 的指数到达间隔，25% 长请求。固定四个活跃槽，一步的虚拟耗时为 `2+0.5×活跃数` ms。短请求 4 个 prefill 步和 12 个 decode 步，长请求 24+48 步。有界队列最多等 8 个，无界队列不主动拒绝；两者都有 1 秒截止时间，每 17 个请求有一个在 100 ms 后主动取消。

逐步模拟入队、准入、prefill、decode、完成、取消、超时，终态只出现一次。移出 active 就回收对应的 KV 页；等待请求还没有占页。计时粒度是一批一步，取消/截止检查最多晚一个步长。所有请求排空后再算观测窗口，不能用到达期做完成吞吐的分母。

- TTFT：从到达到首 token，含排队。
- ITL：相邻输出 token 间隔。
- p95/p99：nearest-rank 分位数，**仅在完成请求上**统计；拒绝、取消、超时另报，避免幸存者偏差。
- goodput：同时满足 TTFT≤200 ms、最大 ITL≤6 ms、完成≤1秒的请求数/观测秒数。
- 资源：队列峰值、KV 页峰值/时间加权均值、最终残留页。

## 运行

```bash
python -m llm_infer.m28_service_capacity.demo
```

## 运行后应该看到什么

扫描 8/24/48/96 请求每秒。48 档时有界队列峰值 8，无界超过 50；有界 goodput 约 16.5 请求/s，无界约 1.6。无限排队不提高满足 SLO 的容量。最终所有请求可核对为完成+拒绝+超时+取消，KV 残留为零。

## 边界与自测

毫秒数来自代价模型，没有 GPU 标定；KV 页数随输出增长，未实现真实分页分配。模型暂不模拟网络、动态 chunking、跨卡通信和重试风暴。实际部署应重放真实到达/长度分布，测负载曲线，再选满足 SLO 的容量余量。

为什么拒绝率上升、p99 下降，不足以证明服务更好了？因为可能只是丢弃慢请求，必须同时看 offered load、完成数、goodput 和所有终态。
