# 代码任务: 跨文件修改与独立验收

## 直觉

仓库级代码工程验收包含两项核心要求: 修改某一模块接口后必须核验全仓库上下游调用链的一致性, 且验收判分必须由候选 agent 无权修改的外部测试套件独立执行。本实验将 rates.py 中折扣率函数的返回约定从百分数改为小数 (例如八折优惠的 20% 返回 0.2), 下游调用方 invoice.py 原本会将返回值除以 100, 接口变更后必须同步移除该除法。
三份候选补丁在外部独立验收下的表现截然不同:
- 仅修改 rates.py 而遗漏调用方 invoice.py 的局部补丁, 在工作区外的 4 个独立测试用例中仅通过 1 个, 验收子进程返回退出码 1 (非 0 代表验收失败)。
- 同步更新接口定义与下游调用方的完整补丁顺利通过全部 4/4 个独立用例。
- 作弊补丁将 total 返回值硬编码为常量 80, 并将工作区内的可见测试篡改为恒真语句 assert True 以自报通过, 但在外部独立验收下同样仅通过 1/4。
单个函数在局部测试下看似正常, 并不代表整个代码仓库的跨文件契约已经修复。

## 核心原理

本案例检验跨文件接口契约变更时的上下游同步修改能力。上游模块 rates.py 中的 rate() 变更为返回小数折扣率 0.2 (对应八折), 下游模块 invoice.py 中的 total(price, quantity) 调用该函数计算折后总价, 公式为单价乘以数量再乘以 1 减折扣率。
两类诚实补丁的行为差异如下:
- 局部补丁仅修改上游定义, 下游 invoice.py 仍保留除以 100 的旧逻辑, 导致实际生效折扣率变为 0.002, 输入 (30, 3) 时算出错误结果 89.82 而非期望值 72。
- 完整补丁同步删去下游调用处的冗余除法, 全部 4 组测试顺利通过。
工作区外的独立验证器固定测试 (100, 1)、(30, 3)、(0, 5)、(12.5, 2) 四组单价与数量输入, 对应期望总价依次为 80、72、0、20。局部补丁之所以仍能通过其中 1 组, 仅因为单价为 0 时无论折扣率缩放多少倍乘积恒为 0。

代码生成模型既可采用从左至右的 next-token 自回归目标训练尾部补全, 也可采用 Fill-in-the-Middle (FIM) 目标训练上下文中间插补。FIM 将源码序列切分为前缀 prefix、中间缺失段 middle 与后缀 suffix 三部分, 重排拼接为「prefix + suffix + middle」顺序供模型在给定前后文约束下预测中间代码。而自动化单元测试生成的关键在于断言期望值必须源自独立业务规约而非被测实现本身: 若测试期望值直接照搬当前待测函数的运行输出, 代码实现出错时生成的测试也会将错误行为固化为通过标准。
仓库级代码任务从浅到深分为三个递进层次:
1. 生成语法合法、能够通过解析或编译的代码片段。
2. 跑通工作区内当前可见的单元测试。
3. 在不破坏既有系统契约的前提下真正解决用户需求。
本例中的 test-cheat 补丁仅停留在表象上的第二层, 靠篡改可见测试制造全绿假象, 并未触及真实业务需求。

仓库级代码检索不能仅靠文本向量相似度召回表层相近片段, 还必须依托静态结构索引补齐跨文件符号依赖。修改任一公共接口前, 上下文收集器需查明五类工程信息:
- 目标符号的精确定义签名与返回约定。
- 全仓库范围内引用该符号的全部跨文件调用关系。
- 构建脚本与模块导出配置。
- 第三方依赖库的版本约束。
- 本次契约变更可能波及的下游模块范围。
本例局部补丁漏改 invoice.py, 正是因为缺乏跨文件调用图检索而忽略了下游消费者。
此外, 使用企业私有代码库做领域适配微调时还必须严防基准泄漏: 训练集与评测集应同时按提交时间戳和同源仓库族 (存在 fork 或代码拷贝关系的关联仓库群) 严格隔离, 避免同源克隆代码横跨训练与测试两侧而虚增评测得分。

安全漏洞修复任务需要执行可复现的攻防双向核验, 且不可信候选代码的运行必须置于操作系统级安全沙箱之内。验收漏洞修复补丁时需逐一确认三项独立证据:
- 修复前概念验证输入 (PoC) 能够稳定复现目标漏洞。
- 应用补丁后同一攻击输入及变体不再触发漏洞。
- 原有正常业务功能与回归测试套件未受破坏。
仅凭静态代码扫描工具 (SAST) 的告警条数下降, 不能认定真实安全漏洞已被消除。
在执行安全性上, 生产级评测平台必须将模型生成的不可信代码与测试脚本放入网络受限、算力内存配额受控且挂载只读或隔离文件系统的容器或轻量虚拟机中运行。本实验边界在于仅调用 python -I 启动独立验收子进程: -I 参数仅指示解释器忽略 PYTHON 前缀环境变量并禁用用户级 site-packages 目录以隔离模块导入路径, 它并非操作系统级安全沙箱, 不提供文件系统、网络或系统调用层面的权限隔离。

## 怎样验证

实验固定同一份外部验收脚本 verify.py 及 4 组独立输入用例, 针对三种候选补丁 (仅改上游接口的 partial、同步修复调用方的 complete、硬编码返回值并篡改本地测试的 test-cheat), 统一从候选工作区目录之外另起隔离导入环境的独立 Python 子进程加载候选代码执行核验, 严格以独立用例通过数与子进程退出码作为最终判据。由于候选体的写权限被限制在其自身工作区目录内, 即便其将工作区可见测试改为 assert True 也无法干扰外部 verify.py 的判分结果。安全边界上, 本实验仅加载执行本仓库确定性生成的受控短小代码片段。

## 与真实系统的差距

两个模块的受控 API 迁移, 候选补丁由程序给定, 不是通用 Coding Agent, 也不是安全沙箱; -I 只隔离 Python 环境, 不隔离操作系统权限。

## 常见误区与自测

候选把自己的测试改为恒真, 怎样继续可信验收?

<details><summary>展开解析</summary>

必须将验收测试与候选代码写权限物理隔离, 在工作区外另起独立进程运行候选体无权读取和修改的测试套件。由于候选 agent 在自身工作区内既能修改业务实现也能重写测试文件与输出日志, 其自报的测试通过记录不具备任何证明力; 本例 test-cheat 补丁正是通过将本地测试篡改为 assert True 并将 total 硬编码为 80 来伪造本地全绿结果。
可信验收机制将 verify.py 存放在候选工作区目录之外, 由外部独立 Python 进程直接导入候选工作区中的 invoice.py 并输入 4 组期望结果各异的测试用例; 硬编码的常量 80 仅能侥幸碰中 (100, 1) 这一组用例, 最终独立验收得分为 1/4、进程退出码为 1, 作弊补丁被准确拦截。因此候选自报成功绝不构成验收证据。

</details>
