# 代码任务: 跨文件修改与独立验收

## 直觉

把折扣接口从百分数改成小数后, 只改 rates.py 不改 invoice.py 的补丁, 在工作区外的 4 个独立用例里只过 1 个, 退出码 1; 同步调用方的完整补丁 4/4。候选把 total 硬编码成 80、把本地测试改成 assert True 自报全绿, 独立用例照样只过 1/4。一个函数过了测试, 不等于整个仓库对了。

## 核心原理

案例把折扣接口从百分数改为小数: 只改定义时, invoice.py 还在除以 100, (30, 3) 算不出 72; 完整补丁同步调用方后 4 个用例全过。独立验证器用的是候选改不到的测试, 覆盖 (100, 1)、(30, 3)、(0, 5)、(12.5, 2) 四组价格与折扣组合。

代码模型可以用 next-token 或 Fill-in-the-Middle (prefix/suffix/middle 重排) 训练补全; 测试生成则要看断言是否独立于实现。写出能编译的代码、通过可见测试、解决用户需求是三个不同层次。

仓库级检索要拿到符号、调用关系、构建配置、依赖版本与变更范围。私有仓库适配要防数据泄漏: 按时间和仓库族拆分, 别让同一份代码拷贝同时进训练集和测试集。

漏洞任务要单独核验触发条件、修复与回归, 静态告警数量下降不算安全改善。真实候选代码要在受限容器/虚机里跑, 限制网络、资源和写路径; demo 的 python -I 只隔离导入环境, 不是安全沙箱。

## 怎样验证

固定同一份验收器 verify.py 和 4 个用例, 对 partial / complete / test-cheat 三种补丁分别另起独立 Python 进程验收, 以通过数和退出码判定; 可见测试被改成 assert True 也影响不到外部判分, 本例只运行本仓库生成的可信小片段。

## 与真实系统的差距

两个模块的受控 API 迁移, 候选补丁由程序给定, 不是通用 Coding Agent, 也不是安全沙箱; -I 只隔离 Python 环境, 不隔离操作系统权限。
