# m60 — 跨窗口接力: 新会话从干净上下文开始, 状态写在磁盘上

[Agent 目录](../README.md) · [交互实验](https://beleev.github.io/llm-engineering-lab/#/agent/long-horizon)

## 直觉

任务比一个上下文窗口大的时候有两条路。一条是让一个会话一直跑, 快满了就压缩; m14 的两档瘦身就是这条路。另一条是把状态写到磁盘上, 让每个新会话从干净的上下文开始, 读进度文件和提交记录, 做完一个功能、端到端测过、提交、更新进度, 然后结束。

第二条路有一个额外的理由: 真实 API 上历史只能追加, 本地改写过的历史发回去会让其后的 thinking 块失效 (见 Agent loop 一章的补充段)。压缩是服务端的能力, 自己在本地摘要换掉旧轮并不是免费的。新会话从干净上下文开始, 不改任何已发出的历史, 正好绕开这条约束。

但「开新会话」本身不解决问题。新会话也什么都不知道, 它得有东西可读。本模块用一个确定性模拟比较四种做法, 在同一条总上下文预算下看真正通过的功能数:

- 单个长会话, 只靠压缩: 12 个功能做成 6 个, 回归 19 次, 重做 16 次。
- 新会话但没有交接状态: 同样 6 个, 因为每个新会话都从第一个功能重做一遍。
- 新会话加进度文件, 但不跑测试: 声称完成 12 个, 真正通过 5 个, 虚报 7 个。
- 新会话加进度文件、功能清单和端到端测试: 12 个全做完, 虚报 0, 回归 0, 只用掉 17400 的上下文。

## 核心原理

### 初始化阶段要建四样东西

Anthropic 的做法是让第一个会话 (initializer agent) 只负责搭台子, 产出这四样:

1. 一个启动脚本 (`init.sh`), 后面每个会话靠它把开发服务器跑起来。
2. 一份功能清单, 写成 JSON (模型改 JSON 文件时比改 Markdown 收敛), 每条有描述、验证步骤和一个 `passes` 字段, 初始全部为未通过。claude.ai 克隆那个例子里有 200 多条。
3. 一个进度文件 (`claude-progress.txt`), 记历次会话做了什么。
4. 一次初始提交, 让后面的会话能从 git 看出哪些文件是什么时候加的。

之后每个编码会话 (coding agent) 按同一套步骤开场: 先 `pwd` 确认自己在哪个目录, 读 git log 和进度文件, 读功能清单挑一条优先级最高且未完成的功能, 跑 `init.sh` 起服务, 先做一遍基础的端到端冒烟测试 (把上个会话留下的坏状态先修掉, 不然在它上面加功能只会更糟), 才开始实现。会话结束时写一次提交并更新进度文件。

### 模拟里的机制

12 个功能, 功能 `i` 改动共享模块 `MOD(i) = i % 4`。实现它需要知道同模块已通过功能的约束, 约束的来源只有两处: 本会话自己做过 (还在上下文里), 或者清单里记过 (在磁盘上)。两处都没有, 同模块的已通过功能回归。

`FLAKY(i) = (i % 3 == 2)` 的功能第一次写出来是半成品, 只有端到端跑一遍才会发现并补完。不测就记成完成, 留下坏状态; 后面同模块的功能建在它上面, 也跟着不通过。demo [3] 里半成品是功能 2 / 5 / 8 / 11, 最终不通过的是 2 / 5 / 6 / 8 / 9 / 10 / 11 — 多出来的 6 / 9 / 10 本身写对了, 是被坏状态带下去的。

单个长会话装满之后压缩: 占用降到容量的四分之一, 但上下文里只剩最近 2 条记录。已完成清单和约束一起丢掉, 于是它重做已经通过的功能 (16 次), 也改坏同模块里已经通过的功能 (19 次)。

### 为什么新会话比压缩好, 以及代价

压缩保住的是连续性, 保不住干净的起点。Anthropic 后续那篇文章把这件事说得更直接: 有些模型会出现 context anxiety, 快到自认为的上下文上限时开始提前收尾; 压缩是在原地把早期对话摘要掉, 同一个 agent 接着往下跑, 所以这种焦虑还在。清空上下文换一个新 agent 才给得出干净的起点, 代价是交接产物必须带足状态, 并且每次换会话都要付编排复杂度、token 开销和延迟。

demo [2] 量化了这个代价: 容量从 20000 降到 1600 (每个会话只装得下一个功能), 12 个功能照样全做完, 但会话数从 1 升到 12, 总上下文从 16600 升到 21000。多出来的那部分就是每个会话重新读进度文件的开销。

## 运行

```bash
python -m llm_agent.m60_long_horizon.demo
```

纯标准库, 确定性, 不用随机数, 单线程 CPU 约 0.2 s。

## 与真实系统的差距

- 全部数字来自确定性模拟, 不是实测。上下文占用、实现与测试的开销都是常数, 不随功能变难; 回归只在同一个共享模块内扩散; 压缩只按「只留最近 2 条」建模, 不模拟摘要质量的差别。结论的方向依赖这些假设。
- 不模拟真实的 git, 提交记录只是「哪些功能进了磁盘」的一个布尔集合, 也不模拟用 git revert 回到上一个可用状态。
- 「半成品」按 `i % 3 == 2` 判定, 是一个人为规则。真实情况下一个功能是不是端到端可用, 要靠浏览器自动化之类的工具真的点一遍才知道 — 那篇文章里用的是 Puppeteer MCP, 并且明确提到 Claude 看不见浏览器原生的 alert 弹窗, 依赖这类弹窗的功能因此更容易留 bug。
- 没有建模子 agent。上下文工程那篇把长任务的手段列成三样: 压缩、结构化笔记、子 agent 架构; 子 agent 自己可能烧掉几万 token, 只把 1000 到 2000 token 的摘要交回主 agent。本模块只比较前两样。
- 本仓库的进度文件是模拟里的一个 `set`, 不是真实文件。真实写法要防模型改坏它: 那篇文章用 JSON 而不是 Markdown, 并且只允许模型改 `passes` 字段。
- 没有建模 Anthropic 后续那篇文章的三角色架构 (planner / generator / evaluator), 也没有建模模型自评失效这个现象 — 让 agent 评价自己产出的工作时, 它倾向于自信地夸它。

## 常见误区

- **"换新会话就能接力。"** 新会话什么都不知道。demo [1] 里「新会话, 没有交接状态」这一行和单个长会话一样只做成 6 个, 因为每个新会话都从第一个功能重做一遍。能接力的是磁盘上的进度文件、功能清单和提交记录, 不是「新」这件事本身。
- **"有进度文件就够了。"** 不跑端到端测试时, 声称完成 12 个而真正通过 5 个。进度文件只是把模型的声明记下来, 声明不等于做完 (见 m21); 功能清单之所以要初始全部未通过, 就是为了让「通过」这个状态只能由一次真实的验证来翻转。
- **"压缩和接力是一回事。"** 压缩是在原地把早期对话摘要掉, 同一个 agent 接着跑, 起点不干净; 接力是清空上下文换一个新 agent, 起点干净, 代价是交接产物要带足状态, 并且每次换会话都要重新读一遍。
- **"开新会话总是更省。"** demo [2] 里会话数从 1 升到 12 时, 总上下文从 16600 升到 21000。每个会话读进度文件的开销要重复付, 窗口够装得下整个任务时没有必要拆。

## 自测题

1. 一个新会话打开, 上下文是空的。它要先读哪几样东西才能接着上一个会话干活?

<details><summary>答案</summary>

进度文件、提交记录和功能清单。进度文件说历次会话做了什么, 提交记录说代码现在是什么状态, 功能清单说还剩哪些没通过、下一个该挑哪个。读完之后还要先跑一遍基础的端到端冒烟测试, 确认上一个会话没留下坏状态 — 如果留了, 先修它, 在坏状态上加新功能只会让问题更难找。

</details>

2. 同样的总上下文预算, 为什么单个长会话靠压缩反而做得更少?

<details><summary>答案</summary>

压缩把已完成清单和约束一起丢掉了。demo [1] 里它重做了 16 次已经通过的功能 (不知道它们已经通过), 改坏了 19 次同模块里已经通过的功能 (不知道它们的约束), 修回这些要再花上下文。预算用在这些重复劳动上, 真正推进的功能就只有 6 个。接力做法把这两类信息写在磁盘上, 新会话花 400 个单位读一遍就全知道了。

</details>

3. 功能清单为什么要在初始化阶段就把全部功能写出来, 而且全部标成未通过?

<details><summary>答案</summary>

两个作用。一是给后面每个会话一个明确的终点: 看到一长串未通过的条目, 它不会环顾一圈觉得「已经做了不少, 可以收工了」。二是让「通过」这个状态只能由一次真实验证来翻转: 清单是验收的依据而不是模型的说法, 所以提示里要强硬地禁止它删改条目, 只允许改 `passes` 字段。demo [1] 里不跑测试的那一组正是在这里出问题: 它把 12 条全标成通过, 真正通过只有 5 条。

</details>
