# 评测到发布: 均分变好, 为什么仍要回滚

## 直觉

这组实验模拟一次发布: 旧版和候选版先在同一组 20 道离线题上对比, 候选版的平均分从 0.4 涨到 0.9。但在「关键切片退化」这组里, 两道被标为关键业务的题 (关键切片) 从对变错, 离线门槛直接拦下, 不让发布。其它几组离线通过后, 先把 10% 的流量切给候选版 (灰度):
- 用户反馈没收够时先 hold (保持灰度, 不扩大也不撤)。
- 收够且没问题就 promote (全量上线)。
- 只要线上质量跌到 0.625、p95 延迟 (95% 的请求都比它快) 到 500、平均成本到 0.029 或出现 1 条安全问题, 任一越过门槛就回滚到旧版 0ba6aad826f1。

一次发布可能同时改了模型、提示词、检索索引或工具, 所以要知道变好了什么、伤了谁、出事时退回哪一版。

## 核心原理

离线门槛同时看三样东西, 只要一样不过就拒绝:
- 均分差 delta: 本例候选比旧版高 0.5。
- 配对 bootstrap 区间: 本例健康候选是 [0.3, 0.7], 要求下界不低于 -0.05。区间这样算:
  1. 把同一道题上新旧两版的得分差当作一个样本。
  2. 有放回地重抽 1000 次求平均。
  3. 取中间 95% 的范围。
- 关键切片: 关键题上候选答对的题数不能少于旧版。

「关键切片退化」那组的区间是 [0.2, 0.75], 整个在 0 以上, 但两道关键题退化, 照样被拒。20 道题的区间只描述这份夹具; 真实验收还要代表性的任务、发布前就定好的门槛和足够的统计功效 (样本多到能看出真实差异), 不能反复换数据直到挑出显著的结果。

一个版本由 model、prompt、index、tools 四样共同确定, 把它们一起算一个哈希当版本 id, 回滚时才知道要退回哪一组组合。本例旧版 0ba6aad826f1 和候选 a1f094f7c16c 只差在 prompt 和 index。线上阶段用一批固定请求回放来模拟 10% 灰度, 不碰真实流量。监控有四条红线, 任一越线就回滚:
- 质量低于 0.8。
- p95 延迟高于 250。
- 平均成本高于 0.02。
- 安全问题多于 0。

质量只按已经收到反馈的请求算; 收到反馈的比例不到 80% 时先 hold, 缺失的反馈不能当成成功。

线上失败的样本要回流进回归集 (以后每次发布都要重跑的一组测试), 但要先清洗两步:
1. 按输入文本去重 (去掉首尾空白后算哈希), 同一个输入只收一次。
2. 排除受保护的训练、验证、测试集合里已有的输入, 这样回流的数据不会和已有数据重叠, 最终测试仍然干净。

「线上质量下降」那组有 3 条失败请求, 回放时又重复了一遍, 去重后剩 3 条, 其中 query-0 属于受保护集合被排除, 最终只收 2 条。生产环境还要做实体级去重、隐私处理、标签审核和分布漂移监测, 回流的数据不能直接污染最终测试。

## 与真实系统的差距

固定请求回放模拟 10% 灰度, 没有碰真实流量。配对 bootstrap 复用 m13 的实现; 平均提升抵消不了关键切片退化。回归样本按规范化文本去重、排除受保护集合, 仍需实体级去重和隐私审核; 延迟反馈和缺失反馈分开计数。

## 怎样验证

固定同一组离线题和同一批线上请求, 对比旧版和候选版, 比较六种情形: 关键切片退化、线上质量下降、尾延迟超标、成本超标、安全回归、健康候选。判定看四件事:
- 离线是否通过。
- 线上是否回滚。
- 最后在线的活动版本是哪一个。
- 回归集收了几条、缺失反馈和待到达反馈各几条 (本例各 1 条)。

边界测试见 [test_engineering_completion.py](../../tests/test_engineering_completion.py)。

## 常见误区与自测

候选均分更高, 但关键业务切片更差, 该怎么发?

<details><summary>展开解析</summary>

先拦下来诊断, 不发。门槛要在看到结果之前就定好, 本例的规则是三条都满足才放行:
- 均分不降。
- 配对区间下界不低于 -0.05。
- 关键切片不退化。

这组候选均分涨了 0.5, 区间也在 0 以上, 但两道关键题从对变错, slice_ok (关键切片是否没退化) 为 false, 离线就被拒绝。均分把所有题平均在一起, 关键题上的退化会被其它题的进步盖住, 所以它不能是唯一标准。也不能换一个测试集重新算, 直到结果好看再放行, 那样门槛就失去了意义。

</details>
