# 任务恢复: 旧检查点遇到新代码

一个流程型任务 (agent 按节点一步步往下执行的任务) 停在「等待审批」节点, 状态被存成磁盘上的检查点 (checkpoint); 之后代码升级, 由 v2 执行器读回来继续跑。三类情形:
- 兼容迁移:
  1. 迁移给新增的可选字段补上默认值。
  2. 把状态格式版本升到 2。
  3. 继续执行, 向外部账本提交 1 笔 10 元。
- 四种不兼容: 保存的节点在新代码里被删了、缺了必填字段、工具约定变了、恢复时权限已被撤销, 这四种情形全部在对外提交之前就被拒绝, 外部提交 0 笔。
- 外部提交后强退: 让子进程在外部账本已经记账、本地检查点还没写的时候以退出码 17 强行退出; 重启后先按操作键查到收据, 不再重复提交, 外部仍只有 1 笔、合计 10。

能把旧状态读回来, 不等于能安全地继续旧任务。

## 怎么跑

```bash
python -m llm_agent.m57_checkpoint_migration.demo
```

只用标准库: 临时目录里一个 state.json 检查点, 一个 SQLite 外部账本。「外部提交后强退」会真的起一个子进程, 并让它 os._exit(17)。

## 先看这几件事

- schema_version (状态格式版本) 决定怎么读磁盘上的状态。迁移函数在读回时逐项检查:
  - 格式版本认不认识 (1 或 2)。
  - 保存的节点是否还存在 (await_approval、submit、done 之一)。
  - 金额 amount 是不是正整数。
  - 工具版本和操作键是否还是当初的约定 (tool_version 为 1、operation 为 invoice-1)。

  新增的可选字段可以补默认值, 本例给 summary 补了空字符串; 缺必填字段、未知节点和不兼容的工具约定则直接报错。这些检查都发生在任何副作用 (对外部系统的改动, 这里是记账) 之前, 所以被拒绝的几种情形外部提交笔数都是 0。
- flow_version (业务流程版本) 决定任务按哪套业务规则继续。v2 代码新增了一条规则 (金额超过 20 拒绝), 只对 flow_version 为 2 的任务生效; v1 任务继续按它开始时的规则走, 不会被新代码悄悄改写当初的承诺, 所以只有「新业务版本」那组的「执行新业务规则」读数为是。权限是另一道独立的检查: 恢复时要重新授权, 已经撤销的权限不能从旧检查点继承。本例「权限已撤销」那组的状态格式完全合法, 迁移也通过了, 但重新授权失败, 照样拒绝恢复。
- 向外部服务提交和写本地检查点是两个分开的事务, 两步之间进程随时可能被杀掉。实验真的在两步之间让子进程退出 (os._exit, 退出码 17): 外部账本里已经记了 1 笔 10 元, 本地检查点还停在等待审批。重启后, 执行器先用固定的操作键 invoice-1 去账本里查:
  - 查到已有收据且金额对得上, 就跳过提交, 直接把本地状态补成完成。
  - 金额对不上则报错, 不会将错就错。

  如果每次重试都换一个新的操作键, 或者不先查收据就提交, 重启就会再记一笔。

## 怎样验证

固定一份暂停在等待审批节点、金额 10 的 v1 任务, 交给 v2 执行器恢复, 比较七种情形: 兼容迁移、新业务版本、节点已移除、缺必填字段、工具约定变更、权限已撤销、外部提交后强退。判定看三件事:
- 是否拒绝恢复。
- 外部账本里的提交笔数和合计金额。
- 强退再恢复之后是否仍然只有一笔副作用。

7 张表的「外部提交笔数」要么 1 要么 0, 没有 2。

### 外部提交后强退

| 指标 | 实际结果 |
| --- | --- |
| 拒绝恢复 | false |
| 外部提交笔数 | 1 |
| 外部合计 | 10 |
| 查询已有收据 | true |
| 执行新业务规则 | false |
| 状态格式版本 | 2 |
| 故障子进程退出码 | 17 |

子进程先往账本写了 1 笔 10 元, 还没写本地检查点就 os._exit(17); 磁盘上 node 仍是 await_approval。父进程重新恢复: 按 invoice-1 查到收据 (查询已有收据 = true), 金额对得上, 跳过提交, 直接把本地状态补到 done。账本最终 1 笔, 合计 10。

实验用真实文件、SQLite 和进程强退, 但不恢复任意 Python 栈, 不实现分布式租约, 也不做任意 schema 的自动迁移。原子重命名没有对目录 fsync, 不承诺断电持久性。
