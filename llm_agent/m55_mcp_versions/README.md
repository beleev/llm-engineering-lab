# MCP: 旧握手、新报文与资源端授权

## 直觉

MCP (Model Context Protocol) 定义了模型宿主应用与外部工具服务之间的标准化通信契约, 协议修订版本以日期标识。本组实验令同一客户端分别通过两代协议连接同一工具服务:
- 2025-06-18 版: 采用本地子进程 stdio 管道通信, 按有状态会话顺序执行:
  1. 发送 initialize 请求协商版本与能力。
  2. 发送 initialized 通知完成握手。
  3. 调用 tools/list 获取 2 个可用工具定义。
- 2026-07-28 版: 切换为无状态 HTTP 传输, 每条请求均需在 JSON 正文的 _meta 字段与 HTTP 请求头中同步声明协议版本。

进一步验证异常拦截与执行边界:
- 发送服务端不支持的未知版本号 1900-01-01 时, 服务端返回 HTTP 400 及协议错误码 -32022。
- 访问凭据的目标受众 (audience) 失配或已过期时返回 HTTP 401。
- 凭据缺少所需权限范围 (scope) 时返回 HTTP 403。
- 在主动取消或超过截止时间两种中止场景下, 工具执行器实际落盘提交的外部副作用均为 0 笔。

协议报文协商、资源端凭据鉴权与执行器副作用控制分属三层独立防线, 仅修改版本号日期字符串并不能完成跨版本协议迁移。

## 核心原理

MCP 2025-06-18 依赖连接初建时的有状态握手绑定版本, 而 2026-07-28 改为无状态逐请求自描述并强制校验头体一致性:
- 2025-06-18 会话握手模式 (本仓库 m09 与 core 模块采用该版本): 连接建立后客户端先发送 initialize, 收到响应后再发送 initialized 确认, 协议版本在单次握手中确定并供后续报文隐式沿用。
- 2026-07-28 逐请求携带模式: 移除有状态握手依赖, 每条请求均在正文 _meta 字段中显式携带版本号与客户端能力, HTTP 传输下还必须在 MCP-Protocol-Version 请求头中同步声明; 客户端可预先调用 server/discover 查询服务端公开的 supportedVersions 列表。

服务端通过结构化状态码精确区分契约违例类型:
- 请求头与正文版本或镜像元数据不一致: 返回 HTTP 400 与错误码 -32020。
- 协议版本不在支持列表内: 返回 HTTP 400 与错误码 -32022。
- 调用方法名不存在: 返回 HTTP 404 与错误码 -32601。

此外, HTTP 请求头还须通过 Mcp-Method 与 Mcp-Name 镜像正文中的方法名与目标工具名, 网关或服务端检出头体失配时同样以 -32020 拒绝。

MCP 授权机制按传输通道形态分层解耦, 本地子进程与远程 HTTP 服务采用各自的凭据验证路径:
- stdio 通道: 工具进程作为宿主应用的本地子进程拉起, 直接继承受控宿主环境注入的本地凭据, 不套用远程 HTTP OAuth 授权流。
- HTTP 通道: 启用授权时由资源服务端逐请求核验访问凭据; 本实验采用不透明令牌 (opaque token), 服务端通过查表解析该令牌绑定的目标受众、过期时间戳与授权 scope。

鉴权拦截遵循最小权限准则: 当令牌受众不为 lab-mcp 或已逾有效期 (实验固定服务端时钟为 100, 过期令牌截止时间为 50) 时返回 HTTP 401; 当令牌通过身份核验但 scope 不包含 tools:read 时返回 HTTP 403。实验边界: 本实验未实现完整的用户登录交互与授权服务器令牌签发流程, 仅验证资源服务端的三种准入拒绝路径。

取消信号与截止时间上下文必须一路透传至工具执行器内部并在副作用提交点前强制检查, 客户端单方面断开网络连接并不能自动回滚服务端已发起的写库或扣款操作。本实验的工具执行器在写入外部状态前设置显式门控检查:
- 当前调用上下文是否已收到协同取消标记。
- 服务端当前时钟 (固定为 100) 是否已超过请求携带的截止时间 (超时用例设为 99)。

上述任一条件成立时执行器立即中止落盘, 确保主动取消与执行超时两种场景实际提交的外部副作用均为 0 笔。实验边界: 网络闪断重连、写操作幂等键去重与长任务断点恢复在异步运行时模块中专门展开。

## 运行

```bash
python -m llm_agent.m55_mcp_versions.demo
```

需要 Python ≥ 3.10, 只用标准库和仓库里的 `llm_agent.core.mcp`。HTTP 端点起在 127.0.0.1 的随机端口上, 不出本机; 「2025 stdio」一项会拉起 m09 的 MCP server 子进程。不调用模型 API。

## 运行后应该看到什么

除「2025 stdio」外, 7 种情况都向同一个 loopback 端点发 tools/list, 协议版本写在 _meta 和 MCP-Protocol-Version 头里。「取消/超时后提交」8 行全是 0。

### 2025 stdio

| 读数 | 实际结果 |
| --- | --- |
| HTTP 状态 | "不适用" |
| 协议或授权拒绝 | false |
| 取消/超时后提交 | 0 |

真实子进程 stdio: initialize → initialized → tools/list。协议固定 2025-06-18, 发现 2 个工具。没有 HTTP, 状态写「不适用」。

### 2026 HTTP

| 读数 | 实际结果 |
| --- | --- |
| HTTP 状态 | "200" |
| 协议或授权拒绝 | false |
| 取消/超时后提交 | 0 |

tools/list 返回 200; 接着 server/discover 返回 supportedVersions, tools/call echo 把 "hello" 原样送回。

### 未知版本

| 读数 | 实际结果 |
| --- | --- |
| HTTP 状态 | "400" |
| 协议或授权拒绝 | true |
| 取消/超时后提交 | 0 |

版本写成 1900-01-01: 400, 错误码 -32022, data 里列出 supported 只有 2026-07-28。服务端不会把它按旧报文静默解析。

### 错误受众

| 读数 | 实际结果 |
| --- | --- |
| HTTP 状态 | "401" |
| 协议或授权拒绝 | true |
| 取消/超时后提交 | 0 |

token 的 audience 是 other-api, 不是本服务的 lab-mcp: 401, invalid_token, 响应头带 WWW-Authenticate。

### 凭据过期

| 读数 | 实际结果 |
| --- | --- |
| HTTP 状态 | "401" |
| 协议或授权拒绝 | true |
| 取消/超时后提交 | 0 |

token 的 expires=50, 服务端时钟固定在 100: 401, invalid_token。audience 和过期在服务端是同一条判断, 客户端自报的 claims 不算数。

### 权限不足

| 读数 | 实际结果 |
| --- | --- |
| HTTP 状态 | "403" |
| 协议或授权拒绝 | true |
| 取消/超时后提交 | 0 |

token 合法但 scopes 为空, 没有 tools:read: 403, insufficient_scope。凭据校验过了, 工具权限这一层没过。

### 执行取消

| 读数 | 实际结果 |
| --- | --- |
| HTTP 状态 | "200" |
| 协议或授权拒绝 | false |
| 取消/超时后提交 | 0 |

HTTP 200 之后进工具执行器, cancelled 标志已置位, run() 在提交前返回 cancelled, committed 仍是 0。

### 执行超时

| 读数 | 实际结果 |
| --- | --- |
| HTTP 状态 | "200" |
| 协议或授权拒绝 | false |
| 取消/超时后提交 | 0 |

deadline=99, now=100, run() 返回 deadline, 同样 0 笔提交。

## 与真实系统的差距

HTTP 资源端真的跑在 loopback 上, 但时钟固定在 100, 凭据是服务端写死的 opaque token, 只够做授权反例。没有 OAuth 登录、令牌签发、SSE, 也没有完整的互操作认证。

取消 / 超时检验的是工具执行层的合作停止, 不等于网络断了副作用就自动撤销。stdio 的环境凭据和 HTTP 授权流程是分开的两套。

## 怎样验证

固定同一后端工具注册表与同一语义目标请求 tools/list, 对照测试八种运行工况: 2025 版 stdio 握手调用、2026 版 HTTP 调用、未知协议版本、错误令牌受众、凭据过期、scope 权限不足、执行中途取消以及执行逾截止时间。验收联合核查两项标准:
- 各工况返回的 HTTP 状态码与 JSON-RPC 协议错误码是否与契约定义严格一致。
- 主动取消与超时中止两种工况下, 执行器提交的外部副作用笔数是否严格为 0。

边界测试见 [test_engineering_completion.py](../../tests/test_engineering_completion.py)。

## 常见误区与自测

仅将旧版 initialize 握手请求中的版本日期字符串替换为新版日期, 能否算作完成协议迁移?

<details><summary>展开解析</summary>

不算完成迁移。2025-06-18 版通过单次 initialize 握手在连接生命周期内绑定版本, 而 2026-07-28 版重构了整套无状态报文契约, 版本号日期只是其中的标识字段:
- 逐请求自描述: 每条业务请求均须在 JSON 正文的 _meta 字段内携带协议版本与客户端能力声明。
- 请求头镜像一致性: 走 HTTP 传输时必须在 MCP-Protocol-Version、Mcp-Method 等请求头中同步写入对应元数据, 若头体不一致则直接返回 HTTP 400 与错误码 -32020。
- 能力发现机制迁移: 服务端支持的版本列表与能力集改由无状态的 server/discover 接口按需查询, 不再依赖有状态连接握手协商。

本实验中遇到未识别版本号会直接返回 HTTP 400 与 -32022 并附带受支持版本列表, 服务端绝不会按旧版报文结构静默兼容猜测客户端意图。

</details>
