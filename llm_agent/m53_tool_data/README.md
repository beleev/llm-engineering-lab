# 工具学习: 从候选调用到训练数据

## 直觉

同一个加法工具, 全部收录时留出 40 题全调用, 复述题也被答成 a+b, 只对 20 题; 按有/无工具的答案似然收益过滤后, 只在算术题上调用 (20 次), 40 题全对; 把成本门槛提到 6, 算术题的收益也不够, 0 次调用, 又只对 20 题。工具执行成功, 不代表值得教给模型; 训练数据应保留能帮助后续预测的调用, 并把额外成本算进去。

## 核心原理

Toolformer 式路径先提出插入位置与参数, 执行工具, 再比较有无工具输出时后续 token 的损失, 只保留有收益的调用。工具结果要作为观察插入, 不能伪装成用户授权。

demo 实际执行加法, 用公开的条件读出概率算 log 似然收益 (无工具时算术题答对概率 0.005, 复述题 0.9); 从 80 道训练题的接受标签估计两类上下文的调用频率, 再在 40 道留出题上验收。过滤器在这里是固定规则, 没有训练语言模型。

成本门槛过低会留下无用调用 (全收录: 复述题调工具答错), 过高会丢掉有益调用 (门槛 6: 算术题收益 log(0.9/0.005) 也过不了, 0 次调用)。真实数据还要去重、防答案泄漏、记录工具版本、超时和异常, 再用 SFT loss mask 只监督该学的动作与回答。

## 怎样验证

固定同一批题 (算术、复述各 40 训练 + 20 留出) 和同一个加法工具, 只换 no-filter / loss-filter / cost-aware 三种筛选规则, 比较留出题上的调用次数和正确数; 真实 Toolformer 的候选生成、语言模型条件似然和再训练规模都不在这个小模型结果里。

## 与真实系统的差距

Toolformer 数据构造机制的最小对照。工具输出按观察而不是用户指令插入; 真实场景还要隔离执行、去重, 并计入延迟与权限成本。

## 常见误区与自测

工具执行成功就应该把调用加入训练集吗?

<details><summary>展开解析</summary>

不应该。工具成功只是执行层的事实: demo 里复述题的加法调用全部成功, 收录后留出题反而只对 20/40。筛选还要看后续预测收益、任务正确性、权限和资源成本。

</details>
