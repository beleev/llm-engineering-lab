# m61 — 模型路由与级联: 按每个完成的任务算钱

[Agent 目录](../README.md) · [交互实验](https://beleev.github.io/llm-engineering-lab/#/agent/system-design)

## 直觉

一批 agent 任务有难有易。全交给大模型最省事; 先让便宜的小模型试、失败再升级 (级联, FrugalGPT), 或者先用分类器按预测难度分配 (路由, RouteLLM), 看起来能省钱。

比较这些做法时最容易用错尺子。按每次请求算, 小模型永远便宜; 但它失败的尝试也要付钱, 升级后大模型还要再跑一遍。正确的尺子是两步:

1. 先过同一条完成率门槛 (本模块是 80%), 达不到的策略不参与比价。
2. 再比每个完成任务的成本: 总花费 (含失败尝试) 除以完成的任务数。

在本模块的成本模型里, 同一模型把 effort 从 high 降到 medium, 每个完成任务从 $0.385 降到 $0.250; 小模型按 Haiku 5.5 价位时, 从头换大模型的级联降到 $0.169, 但平均轮数从 6.0 升到 9.9。把失败记录交给大模型接着做的级联按每次请求比单模型 medium 便宜, 按每个完成任务反而更贵 ($0.268), 因为缓存按模型隔离, 接过来的历史要按写入价重读。

## 核心原理

### 每个完成任务的成本

`run` 把一种策略跑完 200 个任务, 返回:

- `rate`: 完成率。
- `per_call`: 总花费 / 模型调用次数, 也就是每次请求的成本。
- `per_done`: 总花费 / 完成的任务数。失败尝试的花费也在分子里。
- `hit`: 缓存读取的输入 token / 全部输入 token。
- `turns`: 平均每个任务跑了多少轮模型调用, 是延迟的代理量。

单看 `per_done` 也会误导: 只用小模型的 `per_done` 只有 $0.014, 因为它只完成最简单的 35%。所以先用 `FLOOR` 过滤, 再比价。

### 成本模型

`attempt` 模拟一次 6 轮的 agent 循环, 每轮的输入由三部分组成: 共享前缀 (system + tools, 6000 token)、本次尝试已有的历史、每轮新增的 2000 token。价格取 Claude 当前价目表的比例:

| 角色 | 价位 | 输入 / 输出 ($/1M) |
|---|---|---|
| 大模型 | Opus 5.5 | 4 / 20 |
| 中模型 | Sonnet 5.5 | 2 / 10 |
| 小模型 | Haiku 5.5 | 0.10 / 0.50 |

缓存读按 0.1 倍、写按 1.25 倍计。一轮的花费是:

$$\text{cost} = \big(\text{hit} \times 0.1 + \text{write} \times 1.25\big)\, p_{\text{in}} + \text{out}_{\text{effort}}\, p_{\text{out}}$$

hit 是这一轮能从缓存读到的输入, write 是要新写入的输入, $p_{\text{in}}$ 与 $p_{\text{out}}$ 是每 token 单价, $\text{out}_{\text{effort}}$ 是该档 effort 每轮的输出 token (low 400、medium 900、high 2000)。

任务难度按分位数均匀摆在 [0, 1] 上, 不用随机数; 模型在某档 effort 下有一个能力阈值 `CAP`, 难度不超过它就算完成。

### 级联为什么会丢缓存

prompt cache 按模型隔离。级联升级时有两种做法:

- 从头换大模型: 大模型重新开始这一任务, 花费与直接交给它一样, 浪费的只是小模型那一次尝试。
- 把记录交给大模型接着做: 小模型留下的历史在大模型的缓存里没有, 第一轮要按 1.25 倍写入价全部重读, 之后每轮的上下文也更长。

`attempt` 的 `carried` 参数就是这段被重新写入的历史。

### 路由

`router_noise` 给每个任务的难度加一个确定性的预测误差 (标准差 σ), 预测为简单的任务走级联, 其余直接交给大模型。路由省的是小模型注定失败的那次尝试: 完美路由 (σ=0) 平均 6.0 轮, 级联 9.9 轮。省下的钱则取决于小模型的价位: Haiku 价位下小模型那次尝试几乎免费, 级联反而比完美路由便宜; Sonnet 价位下路由更便宜。

## 运行

```bash
python -m llm_agent.m61_model_routing.demo
```

纯标准库, 确定性, 单线程 CPU 约 0.2 s。

## 与真实系统的差距

- 全部数字来自确定性的成本模型, 不是实测。能力阈值 `CAP`、每轮 token 数和任务难度分布都是假设值, 只有价格比例取自 Claude 当前价目表; 结论的方向依赖这些假设, 不能当成某个真实模型的成本数据。
- 完成与否是阈值判定 (难度 ≤ 能力), 没有随机性, 也没有 pass^k 意义上的多次运行波动。
- 级联的验收器是完美的: 失败一定被发现、成功一定被接受。真实验收器会漏判, 漏判的错误结果会被当成完成, 级联的真实完成率低于这里的数字。
- 不计路由分类器本身的开销。RouteLLM (arXiv 2406.18665) 用偏好数据训练路由器, 报告在部分场景下成本降到一半以下而回答质量不降; FrugalGPT (arXiv 2305.05176) 的级联报告最多省 98% 的成本而质量与 GPT-4 相当。两者的场景都是单轮问答, 本模块是多轮 agent 任务, 数字不能直接对照。
- 缓存只模拟了前缀读写倍率与按模型隔离, 没有 TTL、最小可缓存长度和断点数上限 (见 m19)。
- 跨模型时 thinking 块能不能被下一个模型读到 (Opus 5.5 读不了 Fable 的块, 只有少数模型读得了 Opus 5.5 的块) 没有模拟; 读不到的块会被 API 丢弃, 下一个模型要重新规划, 真实代价比这里高。
- 延迟只用平均轮数近似, 没有把等待时间折算成钱。

## 常见误区

- **"小模型单次便宜, 先用小模型一定省钱。"** 要按每个完成任务算: 把失败记录交给大模型接着做的级联, 每次请求比单模型 medium 便宜 35%, 每个完成任务却贵 7%。
- **"级联换模型接着做, 省掉了重做的钱。"** 缓存按模型隔离, 小模型留下的历史在大模型那里要按写入价重读, 之后每轮的上下文也更长; 本模块里从头换反而比接着做便宜。
- **"降 effort 只会让结果变差, 不如换小模型。"** 同一模型降 effort 不换缓存、不丢 thinking 块, 是最直接的旋钮; 级联是否更划算取决于价差和简单任务占比, Sonnet 价位、简单任务只占 10% 时级联比完成率相同的单模型 medium 还贵 2%。

## 自测题

1. 只用小模型的每任务成本 $0.014, 是所有策略里最低的, 为什么不选它?

<details><summary>答案</summary>

它的完成率只有 35%。每个完成任务的成本只在完成率过了同一条门槛之后才可比; 剩下 65% 的任务没有完成, 它们要么交给人, 要么换别的模型重做, 这些花费都不在 $0.014 里。

</details>

2. 级联升级时, 为什么「把失败记录交给大模型接着做」比「从头换大模型」更贵?

<details><summary>答案</summary>

prompt cache 按模型隔离。小模型跑了 6 轮留下的历史在大模型的缓存里没有, 大模型第一轮要把它们按 1.25 倍的写入价全部重读, 之后每轮的上下文也多出这一段。从头换时, 大模型只读共享前缀 (已缓存) 和自己的新历史, 花费和直接交给它一样。

</details>

3. 路由和级联都把难任务最终交给大模型, 路由的好处是什么? 什么条件下它不比级联省钱?

<details><summary>答案</summary>

路由在动手之前就把预测为难的任务直接交给大模型, 省掉小模型那次注定失败的尝试, 平均轮数从 9.9 降到 6.0 到 6.9 (取决于预测误差)。但省下的钱等于小模型那次尝试的花费: 小模型按 Haiku 价位时这次尝试几乎免费, 而路由会把一部分小模型其实能做的任务也交给大模型, 级联的每任务成本 ($0.169) 反而低于完美路由 ($0.177)。

</details>
