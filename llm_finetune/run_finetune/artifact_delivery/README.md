# 模型交付: 新进程里还是同一个模型吗

## 直觉

这组实验把一个训练好的小模型打成交付包, 再在另一个全新的 Python 进程里加载, 看它还是不是同一个模型。比较三样东西:
- 输入被切成的 token 编号。
- 模型输出的 logits (模型给下一个 token 的每个候选打的分)。
- greedy 生成结果 (每一步都取分数最高的 token)。

三组结果:
- 完整 FP32 (32 位浮点) 权重三样全部一致, logits 最大误差 0.0。
- 先压成 int8 (8 位整数) 再还原的权重, token 和生成结果仍然一致, logits 最大误差 0.008654。
- 如果把词表里 a、b 两个 token 的顺序对调, 哪怕同时更新了文件摘要 (sha256 算出的文件指纹), 新进程也拒绝加载。

权重只是一堆数字, 怎么把文字变成 token、怎么套模板、生成到哪里停, 这些约定必须和权重一起交付, 并在加载时核对。

## 核心原理

交付包的目标是: 收到的人不靠口头说明, 就能在自己的机器上还原出同一个模型。包里要带上这几类东西:
- 权重只是参数的数值, 光有它连模型都搭不起来, 所以先要有架构配置 (几层、多宽、几个注意力头)。
- 要把文字切成同样的 token, 还得带上词表和特殊 token (例如开头标记 bos、结尾标记 eos), 以及对话模板 (用户输入前后要加哪些角色标记)。
- 要生成同样的结果, 还要带上生成参数 (最多生成几个 token、是否随机采样)、基座标识 (这份权重是从哪个基座模型训出来的, 本例是 tiny-llama-seed21) 和量化格式 (权重存成浮点还是 int8)。

还要看交付的用途:
- 如果交付是为了接着训练, 还要加上优化器状态和随机数生成器 (RNG) 的状态。
- 如果是为了推理, 就要证明新进程解释输入的方式和训练时一样。

要在一个全新的 Python 进程里加载交付包, 重跑同一条输入, 才能确认还是同一个模型。本例的做法:
1. 把一个很小的 LLaMA 结构模型 (词表只有 8 个 token, 只有 1 层) 训练 25 步。
2. 导出成交付包。
3. 用 subprocess 起新进程去加载。
4. 新旧两个进程对同一条输入 ab 各跑一遍, 对照三项:
   - token 编号是否相同。
   - logits 的最大差值是多少。
   - greedy 生成的 token 是否相同。

int8 这一组在导出时把每个权重张量按它的最大绝对值缩放成 -127 到 127 之间的整数, 加载时再乘回比例还原成浮点数, 所以 0.008654 是这次压缩再还原带来的误差 (验收容差是 0.15)。还原之后的计算仍然在浮点上做, 没有用整数矩阵乘, 所以这个实验不能说明 int8 让推理变快。

文件摘要只能发现文件坏了或被换了, 证明不了内容还是当初约定的那一份。实验里故意改了 package.json (对调词表、改模板结尾、换基座名三种), 同时把 manifest (交付清单) 里记的摘要也更新成新值, 所以摘要校验照样通过。拦住它们的是 manifest 里另存的一份约定副本: 加载时把 package.json 和这份副本逐项比对, 不一致就报「配置与交付约定不一致」并拒绝加载。这个办法的前提是 manifest 本身从可信渠道拿到。真实系统里还有两件事:
- adapter (在基座上微调出来的一小份增量权重) 还要绑定基座权重的摘要。
- 换一个推理引擎时允许多大误差, 也要用一批校准输入实测出来。

## 与真实系统的差距

拒绝时误差显示 0 代表未运行推理；int8 是反量化后的误差实验，没有整数算子加速。manifest 需由可信渠道提供；签名、真实 adapter 基座指纹与跨引擎容差属于部署扩展。

## 怎样验证

固定同一个训练好的小模型和同一条输入 ab, 比较五种交付: 完整 FP32、int8 压缩再还原, 以及故意做错的词表、模板、基座三种错配。判定标准:
- 前两种要求新进程里的 token 和 greedy 生成结果完全一致, logits 误差在容差内 (FP32 小于百万分之一, int8 小于 0.15)。
- 后三种必须在加载时明确报错拒绝, 不能悄悄加载成功、再给出不一样的答案。

边界测试见 [test_engineering_completion.py](../../../tests/test_engineering_completion.py)。

## 常见误区与自测

同一份权重换了词表顺序, 文件摘要也跟着更新了, 能直接上线吗?

<details><summary>展开解析</summary>

不能, 原因有两点:
- sha256 摘要是文件内容的指纹, 文件哪怕只改一个字节, 指纹就对不上, 所以它能发现文件损坏或被调包。但改文件的人可以顺手把清单里的指纹也改成新值, 这时摘要校验照样通过, 它证明不了内容还是当初约定的那一份。
- 词表顺序一换, 同一个字母 a 会被编成另一个 token 编号, 模型拿到的输入就变了, 答案也会跟着变。

实验里对调 a、b 并重算摘要之后, 拦下它的是 manifest 里那份约定副本, 新进程直接拒绝加载。真实交付还要把 adapter 绑定到基座权重的摘要上, 换推理引擎时的误差门槛也要用校准输入实测。
