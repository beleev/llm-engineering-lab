# M17 — 预训练数据流水线: 去重 · 质量过滤 · 配比采样

运行: `python -m llm_train.m17_data_pipeline.demo`

## 直觉
网页语料里同一篇文章被转载几十次, 每次改几个字、换个页脚。模型会把它背下来, 算力也白花了。

- **精确哈希**: 只认逐字相同, 改一个词就漏掉。
- **MinHash + LSH**: MinHash 把 "两篇文档的 5-gram 集合有多像 (Jaccard)" 压成 128 个整数。LSH 再按签名分桶, 只比较落进同一个桶的文档, 不用两两全比。

去完重还有垃圾页: 太短、符号刷屏、同一句话重复几十遍、关键词堆砌。Gopher / C4 用几条便宜的规则拦掉大部分。

最后是配比。按原始 token 比例采样, 2M token 的数学语料只占 0.2%, 几乎见不到。温度采样 `p_i ∝ n_i^(1/T)` 把小语料抬上来, 代价是小语料被重复很多遍。

## 核心数据结构与控制流
- `demo.py:shingles` — 词级 5-gram → crc32 整数集合 (不用 `hash()`, 它每个进程加盐)。
- `demo.py:minhash_signatures` — `[文档数, 128]` 签名, 第 j 位 = `min_x (a_j·x + b_j) mod p`。
- `demo.py:lsh_dedup` — 签名切 32 段 × 4 行 → 每段分桶 → 同桶成候选 → 签名估 Jaccard ≥ 0.5 才算重复 → `union_find_removed` 每簇留下标最小的那篇。
- `demo.py:exact_dedup` — 对照组: 整篇 crc32。
- `demo.py:quality_reasons` — 返回命中的规则列表, 空 = 通过。
- `demo.py:temperature_weights` / `demo.py:credit_sampler` — 温度配比 / 确定性 "额度" 调度。

## 核心公式
```
P[minhash_j(A) == minhash_j(B)] = Jaccard(A, B)
LSH 成候选概率 = 1 − (1 − s^r)^b,   阈值 ≈ (1/b)^(1/r)       (b=32, r=4 → 0.42)
温度采样 p_i = n_i^(1/T) / Σ n_j^(1/T);  上采样倍数 = p_i / (n_i/Σn);  过几遍 = p_i · 预算 / n_i
```

## 与真实系统的差距 (诚实边界)
- 垃圾是按 5 种模式合成的, 规则一眼就能分开, 所以拦截率是 1.000。真实网页没这么干净: FineWeb / DCLM 在规则之后还要跑一个质量分类器。规则本身也会误杀。
- 代码被误杀 100% 是真实问题。为网页调的规则 (符号比例、停用词、词长) 不适合代码、表格、数学。实际做法是按来源分流, 各走各的过滤。
- 模板页 (共享页头页脚的不同页面) Jaccard 0.32, 本例一篇没误杀。模板占比更高时, 它们会被当成重复删掉。这是阈值选择的权衡。
- 真实去重在数十亿文档上跑: 签名分布式计算, 分桶用 shuffle, 连通分量用分布式并查集。还有句子级 / 段落级去重 (后缀数组), 本例没有。
- 温度 T 和各源权重在真实系统里要靠小模型消融实验定 (DoReMi、RegMix)。本例只演示公式的效果。25 遍的 math 很可能已经过拟合。

## 常见误区
- "精确去重就够了" —— 本例只抓到 1/4 的重复。
- "LSH 的阈值就是校验阈值" —— LSH 只决定谁被比较 (S 曲线), 最终判定靠校验。两者分开调。
- "上采样越多越好" —— 小语料重复 4 遍以上收益递减, 再多开始背诵 (Muennighoff 2023)。

## 自测题
1. b=32 段、r=4 行, Jaccard 0.6 的一对成为候选的概率? **答: 1 − (1 − 0.6⁴)³² ≈ 0.988。**
2. 为什么 shingle 哈希用 crc32 不用 Python `hash()`? **答: `hash(str)` 每个进程随机加盐, 两次运行签名不同, 去重结果不可复现。**
3. T=5 时 math 被上采样约 51 倍, 预算 500M token 下它被过几遍? **答: 0.102 × 500M / 2M ≈ 25 遍。**
