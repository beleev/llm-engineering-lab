# DeepSeek-V4 — 压缩稀疏注意力: 先把序列压短, 再在块上选

[llm_models 目录](../../../README.md) · [交互实验](https://beleev.github.io/llm-engineering-lab/#/models/compressed-attention)

## 直觉

- V3.2 的 DSA 用一个便宜的 Lightning Indexer 在 token 上选 top-k, 省的是主注意力的算力。KV cache 一点没省: 每个历史 token 的 latent 还得留着, 还要多存一份 indexer 的 key。
- V4 把选择的粒度从 token 换成块: 每 `m` 个 token 先压成一个压缩条目, indexer 在条目上选 top-k。缓存的东西从 "每 token 一份" 变成 "每 `m` 个 token 一份"。
- 压缩比不能一味开大: 块里的细节被加权和抹平了。V4 的办法是两种层交错 ——
  - **CSA (Compressed Sparse Attention)**: `m = 4`, 块与块重叠, indexer 选 top-k。
  - **HCA (Heavily Compressed Attention)**: `m' = 128`, 不重叠、不选, 稠密读全部压缩条目 (条目本来就少)。
- 另外每个 query 都额外读最近 `n_win = 128` 个未压缩的 token。压缩条目要等它覆盖的 token 全部到齐才可见, 所以 query 附近那一段只能靠这条滑动窗口分支补上。

## 核心原理

### 压缩器: 学出来的加权和, 不是池化

每个 token 先投出一个 KV 向量 `C` 和一个压缩打分 `Z`, 一个压缩条目是它覆盖的那些 token 的 softmax 加权和, 权重里还加了一组按块内位置学的偏置 `B`:

```
S = softmax(Z + B)
C^Comp_i = Σ_j S^a_j ⊙ C^a_j + Σ_j S^b_j ⊙ C^b_j        # CSA: 两路 KV 序列, 块与块重叠
         = Σ_j S_j ⊙ C_j                                 # HCA: 一路, 不重叠
```

CSA 的条目 `i` 覆盖 `2m` 个 token: 自己这一块走第一路, 前一块走第二路。条目是一个向量, 同时当 key 和 value 用 (shared-KV 的多查询注意力), RoPE 只转它的最后 64 维。query 侧是低秩投影再升到多头, query 的每个头和这唯一的 KV 头进注意力之前各过一次 RMSNorm。

本库的 `block_bias` 初始为 0, 所以起步时压缩器就是块内平均池化; 偏置和打分一起训练之后才变成"有选择的"加权和。

### 因果性: 块要凑满才可见

```
条目 i 的到齐位置 = (i+1)m − 1
位置 t 能看到的条目数 = (t+1) // m
```

条目覆盖的 token 全部到齐之前, 它不进任何注意力。所以 `m` 越大, query 前面悬空的那一段越长 —— 最坏情况是 `m − 1` 个 token 还没进任何可见条目。这段空缺由滑动窗口分支补上: 它读的是未压缩的 token, 一个也不丢。HCA 的压缩比敢开到 128, 靠的就是同一条滑窗分支。

### indexer: top-k 不可导, 要单独训

和 V3.2 的 DSA 完全同一套: top-k 是离散操作, LM loss 对 indexer 的梯度全为 `None`。解法是给 indexer 一个对齐损失, 让它拟合主注意力在压缩条目上的分布:

```
p = 主注意力各头在条目上的概率均值 (detach, 再在用到的条目集合上归一化)   # 老师
q = softmax(indexer 打分)  (同一集合上)                                  # 学生
index_loss = KL(p ‖ q)
```

indexer 的输入也 detach 过, 所以 `index_loss` 的梯度只落在 indexer 自己和它的 query 投影上, 不改主干。训练按 V3.2 的三段推进: 稠密预热 → 冻结主模型只训 indexer → 切到稀疏联合训练。

### KV cache 的算式

一个压缩条目按原文的混合精度存: RoPE 那 64 维用 BF16, 其余 448 维用 FP8, 共 576 字节。于是每 token 每层:

```
CSA 层: 576 × ceil(T/4) / T   + 128 × 2 × 576 / T
HCA 层: 576 × ceil(T/128) / T + 128 × 2 × 576 / T
```

滑窗条目有各自的 K 和 V, 条数封顶在 `n_win`、不随长度增长, 所以 `T` 一大它就摊薄了。原文给了一句相对比较: 滑窗条目大约是压缩条目的 8 倍大 —— 在上面这套算式下这个比值恰好是 `2m = 8`。

```
层排布 CCCC (这个玩具四层都用 CSA, 好把检索逼到压缩块上; 原文是 CSA 与 HCA 交错); 压缩比 4 → 16 块, top-k 4, 滑窗 4

```

- 两个召回数字是 "命中针自己那一块" 和 "命中它或它后一块"。CSA 的块重叠, 针所在的 token 既进自己那一块的第一路, 也进后一块的第二路, 所以第二个数才是机制上完整的口径, 它的随机基线也更高 (0.450 对 0.250)。
- 稠密预热之后 indexer 还没训过, 召回停在随机水平 (0.285 / 0.407); 冻结主模型、只用对齐 KL 训 250 步之后升到 0.446 / 0.523, 两个口径都超过各自的基线。
- 从稠密切到只读 top-4 个条目, 不再训练, 答案准确率从 0.875 掉到 0.848; 再联合训练 150 步到 1.000, lm_loss 0.0029。
- 答案准确率到 1.000 并不要求每一层都选中针那一块: 四层各选各的 top-4, 信息可以在层间中转, 而且滑窗分支一直全读。这也是召回只有 0.41 而准确率已经满分的原因。
- 边界: 单种子, 4 层、d_model = 64、序列长 64 的合成检索任务。原文的 1M 上下文、61 层、1024 个候选条目与这里不是一个量级, 这里只验证机制成立。

断言: 初始 lm_loss ≈ ln V、LM loss 对 indexer 的梯度全为 None、index_loss 只给 indexer 非零梯度而主模型为零、稠密预热后 lm_loss 明显下降、预热后对齐 KL 下降且「两块之一」的召回高于随机基线、稀疏训练后 lm_loss 继续下降且召回仍高于基线。

「命中针自己那一块」这个更严的口径只打印不断言: 针落在压缩块边界时, 选中它后一块也能拿到它, 所以这个指标比「两块之一」波动大得多。本机 indexer 预热后它从 0.285 升到 0.446 (基线 0.250), 换台机器见过从 0.302 降到 0.246, 而同一次运行里「两块之一」仍从 0.499 升到 0.565 (基线 0.450)。

## 与真实系统的差距

- **规模**: 4 层、d_model = 64、条目维度 32、序列长 64。V4-Pro 是 1.6T 总参数、49B 激活、61 层、128 个 query 头、头维 512、1M 上下文, 预训练 33T token; V4-Flash 是 284B / 13B / 43 层。
- **层排布**: 原文说 V4-Pro 前两层用 HCA、之后 CSA 与 HCA 交错, V4-Flash 前两层用纯滑动窗口注意力。原文没有给交错的具体比例; 本库用 pattern 字符串按层指定, 没有实现那两层纯滑动窗口。
- **indexer 的 query**: 原文让它与主 query 共用同一个低秩 latent, 本库给 indexer 单独一个投影, 因为库里的 `LightningIndexer` 要求 query 和 key 的输入维度相同。
- **没有 attention sink**: 原文式 27 还给每个 head 一个可学的 sink logit, 本库没有实现 (机制见 GPT-OSS 一章)。
- **稀疏是模拟的**: 仍然构造显式的 `[B, T, S]` 布尔掩码再填 `-inf`, 没有真的跳过矩阵乘。工业部署靠自定义 kernel。
- **不支持 padding**: 压缩条目会把 pad token 混进加权和, 所以 `forward` 遇到带 0 的 `attention_mask` 会抛 `NotImplementedError`。
- **第三项改动没做**: V4 的三项升级是压缩注意力、mHC 残差、Muon 优化器。本库实现前两项 (`residual="mhc"`), Muon 不涉及。
- **本库约定**: Pre-LN、weight tying、embedding 乘 √D、N(0, 0.02²) 初始化, 不代表原模型的做法。

## 常见误区

1. **"CSA 就是把 DSA 的 top-k 换个名字"**: DSA 在 token 上选, 缓存仍是每 token 一份; CSA 在压缩条目上选, 缓存变成每 `m` 个 token 一份。省的东西不同: DSA 省算力, CSA 同时省算力和缓存。
2. **"压缩器是平均池化"**: 它是 softmax 加权和, 权重由每个 token 的压缩打分加一组按块内位置学的偏置决定。本库的偏置初始为 0, 所以起步时才等于平均池化。
3. **"HCA 压缩比 128, 细节肯定丢光了"**: HCA 层也有滑动窗口分支读最近 128 个未压缩 token, 近处一个也不丢; 丢的是远处的细节, 这正是要和 CSA 层交错的原因。
4. **"条目一压好就能用"**: 条目 `i` 要等位置 `(i+1)m − 1` 才可见。实测位置 2 看到 0 条、位置 3 才看到 1 条; 不然就是未来信息泄漏。
5. **"indexer 可以跟着 LM loss 一起训"**: top-k 是离散的, 实测 LM loss 对 indexer 参数的梯度全为 `None`。必须给它一个单独的对齐损失, 而且输入要 detach, 否则主干会反过来迁就筛选器。
6. **"召回率越高模型越准"**: 实测召回 0.41 时答案准确率已经是 1.000。多层各选各的 top-k, 信息可以在层间中转, 滑窗分支也一直全读; indexer 只要好到 "该读的块落在 k 个里面" 就够了。

## 自测题

1. CSA 的条目 `i` 覆盖哪些 token? 它从哪个位置起可见?
   **答**: 覆盖 `[(i−1)m, (i+1)m)` 共 `2m` 个 token: 自己这一块走第一路 KV 序列, 前一块走第二路, 所以相邻块重叠。可见位置是 `(i+1)m − 1`, 也就是自己这一块的最后一个 token 到齐之后; 位置 `t` 能看到 `(t+1) // m` 个条目。
2. 为什么压缩比开大之后更需要滑动窗口分支?
   **答**: 条目要等覆盖的 `m` 个 token 全到齐才可见, 所以 query 前面最多有 `m − 1` 个 token 还没进任何可见条目。滑窗读的是未压缩 token, 正好补上这一段。HCA 的 `m' = 128` 能成立就是因为同一条滑窗分支保住了近处的细节。
3. 按原文配置 (`c = 512`, RoPE 段 64 用 BF16、其余 FP8, `n_win = 128`), 1M 上下文下 CSA 层和 HCA 层每 token 每层各是多少字节? 和 MLA 比呢?
   **答**: 一个条目 `64 × 2 + 448 × 1 = 576` 字节。CSA 层 `576 / 4 + 128 × 2 × 576 / 10^6 ≈ 144.15` 字节, HCA 层 `576 / 128 + 同样的滑窗 ≈ 4.65` 字节。MLA 是 `(512 + 64) × 2 = 1152` 字节, 所以 CSA 层约是它的 1/8, HCA 层约是 1/248。
